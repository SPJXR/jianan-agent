## 一、问题陈述

**谁**：建筑行业的施工安全员、项目经理、监理工程师、施工员，以及编辑出版/政务服务人员。

**什么场景遇到什么痛点**：

1. **查条款慢**：施工安全现场检查、专项方案编制、安全教育培训中，从业者需要引用准确的法规条款（如有限空间作业检测要求、特种作业人员持证规定、危大工程管理要求）。现行做法是在 34 份建安法规文档、住建部官网、地方住建局网站之间来回翻找，一次检索平均耗时 10 分钟以上，且不确定找到的版本是否现行有效。

2. **通用 AI 不可信**：直接问通用大模型（豆包/Kimi/DeepSeek），回答存在幻觉风险——编造不存在的条款号、混淆已废止与现行法规，重要内容必须人工二次核对，等于没省时间。实测横评显示，通用 AI 面对上百页专业 PDF 时细节失真、多轮追问后逻辑偏移的问题普遍存在。

3. **政务咨询响应慢**：住建部门户网站政务咨询栏目中大量问题本质是"某情形适用哪条法规"的简单检索问题，但人工回复周期以周计，无法满足工地现场的即时需求。

4. **现有垂直平台不解决问题**：建标知网覆盖全住建领域但平台重（注册+APP+小程序），以标准文本检索和文档生成为主；建设通只提供法规列表浏览无智能问答；法律类 AI（得理法搜、法智、通义法睿）只覆盖民法典、诉讼等法律领域，不覆盖建安法规与施工安全规范。

**现在怎么解决的**：翻纸质文件/PDF、问同事和微信群、问通用 AI（不敢直接用）、政务咨询留言（等待久）。

**为什么不行**：慢、不可信、不可溯源。安全检查和整改通知是有法律后果的文书，引用错条款比引用慢更严重。

## 二、目标用户

### 主要用户画像

**画像 A：施工安全员 / 专职安全生产管理人员（持有 C 证）**
- 年龄 28-50 岁，大专/本科学历，工地办公室与施工现场混合办公
- 高频场景：日常安全巡查中确认合规依据（如"临边防护栏杆高度要求"）、开具整改通知时引用条款、编制安全技术交底、准备安全培训材料
- 技术水平：熟练使用微信和手机，会用浏览器但不会配置任何 AI 工具
- 核心诉求：30 秒内拿到"条款原文 + 出处"，能直接抄进整改单
- 使用频率：每日 1-5 次

**画像 B：项目经理 / 项目负责人（持有 B 证）**
- 年龄 32-50 岁，本科为主，项目办公室办公
- 高频场景：编制专项施工方案时引用法规、应对检查时快速核实要求、审核安全员提交的整改文书
- 核心诉求：答案准确、引用可核实，能应对上级检查质询
- 使用频率：每周 3-10 次

### 次要用户画像

**画像 C：监理工程师**——审查施工单位报审资料时核对安全条款引用是否准确。
**画像 D：研究者 / 政务服务与编辑出版人员**（用户本人所在群体）——快速定位 34 份文档中关于电子证照标准、禁限用技术目录、开工一件事流程等的具体规定，用于编辑校对与政策答复。

### 反画像（非目标用户）

- 需要全国所有法规标准（数万份）的专业法务——去建标知网
- 需要 US/IBC/OSHA 等国际规范的用户
- 需要 AI 隐患拍照识别的用户（菊安通类产品场景）

### 差评与不足中暴露的市场空白（重点结论）

1. **条款级引用溯源是最大空白**：通用 AI 编造条款号；法律 AI 的"幻觉核验"能力没有被移植到建安法规领域；香港建造业议会产品证明了该模式可行但只在香港。2026 年 7 月发布的"标知"标准大模型同样把"基于 RAG 的溯源问答，所有输出内容均可对应原始标准文献，从根源规避 AI 幻觉"作为核心能力——行业共识已经形成，但建安法规（施工安全）垂直方向没有面向公众的落地产品。
2. **"轻量即开即用"缺失**：建标知网重平台、菊安通区域封闭、浙建内部私有——没有一个小而轻、浏览器打开就能问的建安法规问答 Web 应用。
3. **用户自有文档的知识库化**：用户的 34 份文档包含地方性文件（开工一件事流程、本地电子证照标准等），这些内容不在任何现有产品知识库中，只有"专属知识库"模式能覆盖。
4. **时效性信任**：法规修订/废止频繁，通义法睿的"现行有效"标注思路在建安领域无对应产品。

## 四、我们的差异化

**一句话定位**：一个轻量的、专注建安法规的、每句话都能给出处的小型专属知识库问答助手。

1. **引用溯源可核实**：每条回答标注来源（文档名+条目），附"参考来源"区块展示条款原文片段。用户可点开原文核对——这是与通用 AI 的本质区别，也是安全场景的硬需求。
2. **专属知识库的稀缺内容**：34 份文档中含地方流程文件（开工一件事）、电子证照标准、禁限用技术目录等，全网检索不到、大模型不知道，只有本地知识库能答。
3. **轻量零门槛**：浏览器打开即用，无注册（MVP 阶段）、无 APP 安装、无学习成本——对比建标知网的重平台模式。
4. **答不出就承认**：知识库无相关内容时明确说"未找到直接相关条款"，不编造——把"诚实的不知道"作为产品原则写进验收标准。
5. **成本可控**：用户自备云端 LLM API Key（OpenAI 兼容接口，默认适配阿里云 DashScope），无平台订阅费——对比法律 AI 的年费模式。

**不与谁竞争**：不做全住建领域标准文本库（建标知网主场）、不做隐患图像识别（菊安通场景）、不做企业级私有化平台（MaxKB 生态）。

## 六、MVP 范围

**只做 4 件事**：

1. **法规问答对话（F1）**——检索 + 生成 + 引用标注 + 参考来源区块
2. **流式回答渲染（F2）**——含检索/生成状态提示与失败重试
3. **示例问题引导（F3）**——首屏示例问题点击即问
4. **知识库来源展示（F4）**——34 份文档清单页

**MVP 明确包含的支撑项**（非功能、但必须交付）：

- LLM 配置：API Key、Base URL、模型名通过服务端环境变量/配置文件设置（管理员配置，不在前端暴露 Key 输入）
- 回答免责声明固定文案："回答由 AI 基于本地知识库生成，请以法规原文为准，重要事项请咨询主管部门"
- 34 份文档已完成解析、分块、向量化入库（数据准备由架构师方案承接）

**其余全部进 Backlog**：历史会话、引用展开、多轮追问、反馈、知识库管理、访问口令（见"明确不做清单"）。

## 七、明确不做清单（MVP 阶段砍掉）

| 不做的事 | 理由 |
|----------|------|
| 用户注册/登录体系 | 单机验收 + 小范围公网发布，无多租户需求；注册流程会杀死首访转化 |
| 多用户/团队协作/权限管理 | 无此场景 |
| 文档上传界面（用户自行上传文档） | 34 份文档由开发流程预置入库；开放上传引入解析质量、存储、滥用等复杂度 |
| 隐患拍照识别 | 菊安通场景，与本产品定位不同 |
| 法规全文阅读器/标准文本库 | 建标知网主场，不重复建设 |
| AI 生成整改文书/培训课件 | 模板类功能，验证核心问答价值后再考虑 |
| 前端 API Key 输入框 | Key 属于管理员配置，前端暴露有泄露与盗刷风险 |
| 付费/订阅 | MVP 验证阶段，无商业化需求 |
| 移动端 APP | Web 响应式布局兼容手机浏览器即可 |
| 多知识库切换 | 单一知识库足够 |
| 联网搜索补充回答 | 联网内容不可控，破坏"全部来自本地知识库"的可信承诺 |

## 八、用户故事与验收标准（Given/When/Then）

### F1 法规问答对话（带引用溯源）

**用户故事**：作为安全员，我在工地检查有限空间作业时，需要立即获得法规要求的气体检测标准及条款出处，以便在整改通知中准确引用。

- **AC1.1 标准问答**：Given 用户在输入框输入"有限空间作业前需要检测哪些气体"并点击发送，When 系统完成检索与生成，Then 回答以流式方式呈现，回答正文中包含至少 1 处引用标注（格式如"《有限空间作业安全指南》第 X 条"或"文件名 · 章节"），回答末尾有"参考来源"区块，列出所引用文档名及对应原文片段（片段长度 50-500 字）。
- **AC1.2 引用真实性**：Given 任一回答中的引用，When 用户核对"参考来源"区块原文，Then 引用文字必须逐字来自知识库中该文档的对应片段，不得出现知识库中不存在的条款号或文字。
- **AC1.3 知识库无答案**：Given 用户提问的内容在 34 份文档中无相关条款（如"美国 OSHA 对脚手架的要求"），When 系统生成回答，Then 系统明确回答"知识库中未找到与该问题直接相关的条款"，不得编造法规条文，并提示用户可换个问法或查看知识库来源页。
- **AC1.4 回答结构**：Given 一个可回答的法规问题，When 回答完成，Then 回答结构包含"结论要点 + 依据条款说明"，条理清晰可复制。
- **AC1.5 免责声明**：Given 任一回答完成，Then 回答下方固定展示免责声明文案（见 MVP 支撑项）。

### F2 流式回答渲染

- **AC2.1 状态提示**：Given 用户发送问题，When 系统检索中，Then 输入区上方显示"正在检索法规库"状态提示；检索完成进入生成阶段，提示切换为"正在生成回答"。
- **AC2.2 生成失败**：Given LLM 接口调用失败（Key 无效/超时/额度不足），When 生成中断，Then 界面展示明确错误原因分类文案（如"模型服务暂时不可用，请稍后重试"），并提供"重新生成"按钮，重试仅针对该问题不重复计费语义。
- **AC2.3 中断保护**：Given 用户在生成过程中关闭页面或刷新，When 再次打开，Then 不出现页面报错或僵尸请求（未完成的回答可丢弃，MVP 不要求恢复）。

### F3 示例问题引导

- **AC3.1 空状态展示**：Given 用户首次打开应用且无任何对话，When 页面加载完成，Then 对话区展示欢迎语（说明产品用途与知识库范围）+ 4-6 个示例问题按钮（文字按钮，含文件图标装饰由统一图标方案提供），每个示例问题均能被知识库正确回答（上线前人工验证）。
- **AC3.2 点击即问**：Given 用户点击某示例问题，When 点击发生，Then 该问题自动填入并直接发送，进入 F1 流程。
- **AC3.3 引导文案真实性**：示例问题与欢迎语文案必须基于 34 份文档真实主题生成，禁止使用占位文案。

### F4 知识库来源展示

- **AC4.1 文档清单**：Given 用户打开"知识库来源"入口（页面头部或侧边入口，配文件图标），When 页面加载，Then 展示 34 份文档列表，包含：文档名称、类别标签（如"特种作业/有限空间/考核大纲/禁限用技术/开工一件事/电子证照"）、条目（分块）数量。
- **AC4.2 提示能力边界**：Given 知识库来源页，Then 页面底部说明"回答仅基于以上文档生成"。
- **AC4.3 首屏可见性**：Given 桌面端首屏，Then 知识库来源入口在首屏可见，无需滚动查找。

### 配置与发布（支撑项验收）

- **AC9.1 配置生效**：Given 管理员已在服务端配置 DashScope API Key 与模型名，When 用户提问，Then 系统正常调用云端 LLM 生成回答。
- **AC9.2 配置缺失提示**：Given 未配置 API Key，When 用户提问，Then 返回明确指引文案"管理员尚未配置模型服务"，不暴露堆栈错误。
- **AC9.3 本机验收**：Given localhost 环境完成 F1-F4 全部 AC 验收，Then 才进入公网发布环节（发布由主理人通过平台站点发布流程执行）。

## 九、边界条件

| 场景 | 要求 |
|------|------|
| 空输入/纯空格 | 发送按钮不可用（置灰），不发起请求 |
| 超长问题（>2000 字符） | 输入框给出字数限制提示，超出部分禁止继续输入或提示精简 |
| 知识库无相关内容 | AC1.3：明确"未找到"，不编造；建议相近问法 |
| LLM 超时（>60 秒无首 token） | 按生成失败处理，展示重试按钮 |
| LLM 限流/429 | 错误文案提示"当前提问人数较多，请稍后重试"，自动退避后可手动重试 |
| API Key 无效/额度耗尽 | 错误文案区分提示（联系管理员处理），不暴露 Key 信息 |
| 并发提问 | MVP 不做排队产品逻辑，但前端同一会话同时只允许 1 个进行中的请求（发送按钮在生成期间禁用） |
| 离线/断网 | 前端展示网络错误提示，恢复后可重试 |
| 检索命中为 0 但语义相近 | 走 AC1.3 兜底话术，附带"知识库来源"入口引导 |
| 敏感/无关问题（闲聊、黄反） | 回答限定在法规问答范围："本助手仅提供建安法规知识问答"，不展开闲聊 |
| 极端长回答 | 生成超过预设上限时截断并提示"内容较长，可追问细分问题" |
| 历史会话（Backlog 功能上线前） | 刷新页面后会话丢失属 MVP 已知限制，欢迎语中说明 |

## 十、非功能需求

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 性能 | 页面首屏加载 < 3s（公网）；用户发送问题到首个回答字符流式呈现 < 5s（p95，不含 LLM 完整生成时长）；检索阶段 < 1s | P0 |
| 可用性 | LLM 服务不可用时，检索结果（命中的条款片段）仍可降级展示，并标注"模型服务暂不可用，以下为检索到的原文片段" | P1 |
| 安全 | 公网发布走 HTTPS；API Key 仅存服务端环境变量，不出现在前端代码、网络请求参数与日志中；对 LLM 调用做服务端速率限制（按 IP，如 20 次/分钟），防止 Key 被盗刷 | P0 |
| 兼容性 | Chrome/Edge/Safari/Firefox 最新 2 个版本；移动端浏览器可用（响应式布局，含微信内置浏览器） | P0 |
| 可访问性 | 键盘可完成提问全流程（Enter 发送）；正文对比度满足 WCAG 2.1 AA 基本要求 | P2 |
| 国际化 | MVP 仅简体中文；文案集中管理便于后续 i18n | P2 |
| 内容合规 | 免责声明常驻；回答不构成执法依据的表述在欢迎语与免责声明中固定 | P0 |
| 数据 | MVP 阶段问答记录仅存浏览器本地（如启用历史会话），服务端不留存用户问题明文日志（如需调试日志须脱敏） | P1 |

**视觉规范约束（P0 团队规则）**：
- 功能图标一律使用统一 SVG 图标库（具体库由架构师按项目技术选型锁定，PRD 不预设），PRD 与后续设计稿中以文字描述图标含义（如"文件图标""对话图标""来源图标"），禁止使用 emoji 字符作为功能图标。
- 禁止紫色到粉色的渐变配色方案。参考方向：深蓝/藏青主色传达专业可信（具体色值由设计师输出）。
- 所有界面文案为真实业务文案，禁止"Welcome to""Lorem ipsum"类占位内容。

## 十一、数据埋点方案

MVP 必埋事件（前端轻量 SDK 或自建 trackEvent 封装）：

| 事件类别 | 必埋事件 | 说明 |
|----------|----------|------|
| 获客 | page_view | 首页访问（附 referrer、device 类型） |
| 激活 | first_question_sent | 新用户发出第一个问题（激活定义） |
| 激活 | first_answer_with_citation | 首次收到带引用标注的完整回答（核心价值首次交付） |
| 使用 | question_sent | 每次提问（附问题字数、是否来自示例问题引导） |
| 使用 | answer_completed / answer_failed | 回答完成（附生成时长、引用条数）/ 失败（附错误类型） |
| 留存 | session_start | 会话开始（本地会话 ID） |
| 深度 | source_panel_opened | 打开知识库来源页 |
| 深度 | citation_clicked | 点击引用标注（Backlog 功能上线后） |
| 异常 | error_occurred | 前端错误 + API 错误（脱敏后上报） |

**命名规范**：`{对象}_{动作}`（如 question_sent、citation_clicked）。
**属性规范**：每事件附带 timestamp、device、page_version；不采集可识别个人身份的信息，不上报 IP 明文与用户问题原文（问题原文仅存本地）。
**实现建议**：本地开发阶段可用控制台日志开关；公网发布后接轻量统计（如自建 /open API 计数或 Umami 类方案，由架构师定）。

## 十二、成功指标（MVP 验证期）

| 指标 | 目标 | 说明 |
|------|------|------|
| 激活率：首访用户发出第一个问题的比例 | ≥ 50% | 示例问题引导有效性 |
| 核心价值交付率：提问后收到带引用完整回答的比例 | ≥ 85% | 含检索命中与 LLM 成功率 |
| 引用质量抽查合格率（人工抽检 30 条回答） | ≥ 90% 引用逐字准确 | 引用真实性是产品生命线 |
| 单次提问到首字符响应 p95 | < 5s | 性能底线 |
| "知识库未找到"兜底触发中误判率（实际有答案却答未找到） | ≤ 10% | 检索质量底线 |
| 周提问留存（第二周再次提问的用户比例） | ≥ 30%（参考 SaaS 30 日留存 40-60% 基线的保守折算） | 决定是否进入下一迭代 |

**Go/No-Go 判断**：若激活率与引用质量达标 → 启动 Phase 2（历史会话、引用展开、多轮追问）；若引用质量不达标 → 优先优化分块与检索，不加新功能。

## 十三、风险与开放问题（供主理人/架构师参考）

| 风险/问题 | 影响 | 建议方向 |
|-----------|------|----------|
| 法规文档解析质量（PDF 表格、版式） | 分块错误直接导致引用失真 | 架构师重点评估解析与分块策略（行业经验：RagFlow 类对结构化文档容忍度高；三层漏斗检索为参考模式） |
| LLM 幻觉仍可能在"组织语言"环节引入（即使给了原文） | 引用区块准确但正文表述偏差 | 提示词工程上强制"仅基于给定片段作答"；引用区块与正文一致性纳入人工抽检 |
| 公网发布后的 Key 盗刷 | 资损 | 服务端速率限制为 P0；若发布范围扩大，Phase 2 考虑简单访问口令 |
| 34 份文档中的法规时效性（文档本身是否含已废止版本） | 误导用户 | 知识库来源页标注文档版本/日期；由文档提供方（用户）确认文档集的现行有效性 |
| 示例问题的"可回答性"依赖知识库最终质量 | 首访体验失败 | 上线前人工验证每个示例问题 |
