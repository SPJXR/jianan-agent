## 1. 设计寄存器判定与三轴刻度

### 1.1 寄存器判定：Product（产品寄存器）

依据设计动作命令库 §1 判断流程：

- **路径形态**：本产品是聊天工具界面（类 `/app` 形态），非营销落地页 → Product 寄存器
- **标杆**："赢得熟悉感"——ChatGPT/Claude/通义法睿的熟手用户坐下来就能信任这个界面。失败模式不是平淡，而是无目的的奇怪
- **落地约束**：
  - 调色板 Restrained（克制），强调色只用于主操作、当前选中、状态指示
  - 字体一族为主（Noto Sans SC + Inter 辅助），固定 rem 阶梯
  - 每个交互组件全状态覆盖（default/hover/focus/active/disabled/loading/error）
  - 动效 150–250ms，传递状态而非装饰，无页面加载编排

### 1.2 三轴刻度

| 轴 | 值 | 理由 |
|----|-----|------|
| DESIGN_VARIANCE | **3**（可预测） | 政务严肃场景 + 聊天产品成熟范式，单列居中对话流是用户已建立的心智模型，不需要非对称艺术布局 |
| MOTION_INTENSITY | **3**（功能性） | 仅状态切换 150–250ms + 流式输出的渐进渲染 + 检索步骤指示；无装饰性动画、无入场编排 |
| VISUAL_DENSITY | **5**（日常应用） | 聊天主流程留白舒适（4），回答内容区含引用卡片/条款结构化呈现密度略高（6），取中值 |

### 1.3 品牌声音词（字体选择输入）

按字体选择流程写出三个物理对象词：**"工程图纸的标注文字、法规公文的铅印字形、安全标识的指示牌"**——冷静、严谨、有据可查、零娱乐化。

## 2. 竞品/参照产品调研（5 个对象）

### 2.1 通义法睿（阿里云法律 AI）— 直接竞品参照

**调研发现：**
- 回答采用**分板块结构化呈现**："法律分析 → 行动建议 → 相关法条 → 证据准备"，条理清晰，法条引用具体到条款号（如《劳动合同法》第三十条）
- 检索界面左右分栏：左侧案例/法规列表，右侧 AI 智能洞察
- **法规时效性筛选**是杀手级细节：可筛选"现行有效 / 已被修改 / 已废止失效"，避免适用错误——对法规问答产品是信任关键
- 观韬律所测评指出其弱点：检索结果界面缺少追加提问的交互对话框

**对本项目的借鉴：**
- ✅ 采用"结构化回答 + 法条引用"模式，但简化为适合 MVP 的 2-3 层（结论 → 依据条款 → 实操要点）
- ✅ 引用必须具体到"《法规名》+ 标准号 + 条款号"三元组
- ⚠️ 教训：回答发出后要保留"继续追问"入口，不能中断对话流

### 2.2 Perplexity — 引用 UX 行业标杆（开放域）

**调研发现（AI UX Playground 拆解）：**
- **内联引用 chip**：来源 chip 附在句末（`northjersey +3` 域名优先格式），用户扫读时即可感知溯源；用户研究显示内联引用比页脚堆叠多获得约 40% 的来源检视时长
- **来源行**：回答块底部的 favicon 叠栈 + "10 sources" 计数，与复制/分享按钮同级放置——广度信号在阅读前建立预期
- **检索步骤可见**："Completed 2 steps" 折叠条展开显示"Searching the web → Checking predictions"，用用户心智模型的语言（非 API 名词）展示检索确实发生了——这是检索延迟合理化与信任建立的关键
- 错误来源是**一等失败模式**：负反馈选项包含"Wrong sources"
- 移动端适配：引用编号放大至可点击尺寸，来源列表转为横向滚动 carousel

**对本项目的借鉴：**
- ✅ 句子级内联引用标记 + 底部来源汇总行 + 来源计数，三件套照搬适配
- ✅ 检索步骤可视化，改为政务语境："正在检索 34 份法规 → 定位到 5 处相关条款"
- ✅ 移动端引用编号加大点击区（≥44×44px）

### 2.3 NotebookLM（Google）— 闭域引用标杆（与本项目最契合）

**调研发现（AYDesign RAG citation UX 2026 模式分析）：**
- NotebookLM 把引用视为**闭域问题**（closed-corpus）：锚定在用户上传的固定文档，**常驻来源侧栏 + 直接深链到来源 PDF/doc 的精确段落**
- 与 Perplexity 的开放域（横向来源条+多域名 inline 标记+域名信誉信号）形成两种 UX 语言
- 2026 年 RAG 引用 UX 基线：**inline 编号 chip/上标是所有主流产品（Perplexity/ChatGPT Search/Claude）的公共模式**
- 引用数量指引：单段回答 3–5 个，多段研究式回答 7–12 个；超过 12 个用户不再逐个扫视，依赖聚合信号（来源计数+信任徽章）
- 无障碍要点：标记必须键盘可达，弹层 focus/click 均可打开（非仅 hover），颜色信号必须有文本等价物

**对本项目的借鉴：**
- ✅ **本项目 = 闭域场景**（34 份固定法规文档），NotebookLM 模式比 Perplexity 更契合：引用可深链到文档内精确条款片段并高亮
- ✅ 单条回答引用控制在 3–8 个来源，超过时折叠为"查看全部 N 处引用"

### 2.4 ChatGPT / Claude — 聊天界面的行业语法

**调研发现：**
- ChatGPT 定义了聊天产品的视觉语法：**中性背景、底部锚定输入框、垂直消息流、充分留白、几乎无边框的气泡、克制的 sans-serif**——所有竞品（Claude/Gemini/Grok）布局几乎可叠加，这是"熟悉感=信任"的集体共识
- ChatGPT 引用采用**渐进式深度**：句末 chip → 点击弹 popover（发布者+标题+摘要+1/N 翻页）→ 完整 Sources 侧栏，三层递进不打断阅读
- Claude 的氛围方向：柔和色板、消息间距均匀、用户/AI/系统消息清晰区隔——适合长文阅读（法规条文天然是长文）
- 通用教训：布局趋同不是懒惰而是降低采用门槛；新聊天产品偏离此范式会被感知为"不对劲"

**对本项目的借鉴：**
- ✅ 遵守聊天语法：底部输入锚定 + 单列 768px 消息流 + 中性背景 + 无重边框气泡
- ✅ 引用采用 ChatGPT 式渐进披露：chip 预览（hover/focus 弹层）→ 完整面板（点击）两层即可（MVP 简化）
- ✅ AI 消息不用彩色气泡填充，用头像+留白区隔（Claude 式柔和），法规长文阅读舒适度优先

### 2.5 宁波"甬建智小助" + 建标知网 — 政务建筑场景实证

**调研发现：**
- 宁波住建局"甬建智小助"（建筑业政策咨询智能体）：核心理念是**"所有答复均基于实时更新的法规政策库，确保客观真实、有据可查，杜绝主观臆断"**——与本产品定位一致，验证了"有据可查"是政务建筑场景的第一信任主张
- 建标知网（住建部法规标准平台，kscecs.com）：收录 6000 种标准规范 + 8000 种法律法规，主打"查法规标准、用法规标准"，提供法规 AI 问答——证明建筑法规知识服务的正式产品形态与规模
- 住建部门户/全国工程质量安全监管信息平台的视觉语言：白底蓝头、信息密度高、庄重克制——政务用户对这套视觉有天然的信任感

**对本项目的借鉴：**
- ✅ "有据可查"作为首页欢迎态的核心信任文案方向
- ✅ 视觉气质向政务门户的"白底蓝调"靠拢，而非向消费级 AI 产品的炫彩靠拢

## 3. 对标品牌与设计语言选择

### 3.1 对标组合（按影响权重排序）

| 对标 | 借鉴维度 | 为什么适合建筑法规严肃场景 |
|------|----------|---------------------------|
| **通义法睿** | 结构化回答 + 条款级引用 | 同为"法规+AI 问答"垂类，验证过的专业呈现模式；阿里云产品级严谨度 |
| **NotebookLM** | 闭域引用溯源（深链到段落+高亮） | 34 份固定法规 = 闭域语料，引用可精确到条款片段，这是本产品的信任根基 |
| **Claude** | 聊天氛围（柔和、长文可读、消息区隔） | 法规回答天然是长结构文本，Claude 的排版对长 AI 回答的可读性处理最成熟 |
| **Linear** | 产品级克制细节（边框分层、focus 环、微交互精度） | 政务严肃场景需要的"精密工具感"，避免廉价感 |
| **住建部门户** | 政务信任气质（白底蓝调、庄重） | 目标用户（安全员/施工管理人员）日常接触的权威视觉语境 |

### 3.2 设计语言定义

**关键词：工程蓝图（Blueprint）、有据可查（Verifiable）、政务庄重（Institutional）**

核心隐喻：**工程蓝图**。建筑从业者的职业视觉记忆就是蓝图——深蓝底上的白色精确线条。我们把它反转为浅色界面上"精确、冷静、有标注感"的工程蓝，法规标准号用等宽字体呈现（像图纸编号），引用标记像图纸上的节点标注。这个隐喻同时传达了：专业（工程语境）、精确（条款号）、可信（蓝图是法律性文件）。

**明确避开的路线：**
- ❌ 消费级 AI 产品的炫彩渐变、发光边框、毛玻璃（娱乐化，政务用户会质疑严肃性）
- ❌ 紫粉渐变（P0 红线 + 与工程场景零关联）
- ❌ emoji 图标（P0 红线，建筑安全是执法参考场景，专业度要求极高）

**每屏强调色使用纪律（≤2 处可见 accent）：**
1. 输入框"发送"按钮（accent 实底）+ 句末引用 chip（accent-subtle 浅底）是常规 2 处

- 比 `#2563EB`（blue-600，SaaS 通用）更沉稳，符合"法规"的庄重；比 `#1E3A8A`（法律蓝金 Primary）更亮一点，保留工具产品的活力

### 4.2 字体方案

**配对：Noto Sans SC + Inter（正文与标题同族分工）+ JetBrains Mono（法规编号专用）**

```css
--font-display: "Noto Sans SC", "Inter", -apple-system, "PingFang SC", "Microsoft YaHei", sans-serif;
--font-body: "Noto Sans SC", "Inter", -apple-system, "PingFang SC", "Microsoft YaHei", sans-serif;
--font-mono: "JetBrains Mono", "Fira Code", "Noto Sans Mono CJK SC", monospace;
```

**选择理由（对照字体选择流程）：**
1. 品牌声音词"工程图纸标注文字/公文铅印/安全指示牌"指向：高字面率、笔画均匀、无装饰性曲线的中性无衬线
2. 反射拒绝列表检查：Inter 允许作为正文（仅不允许作为展示字体声称"高级"）——本产品是 Product 寄存器工具，Inter 是正确的工程选择而非偷懒
3. 中文场景 `Noto Sans SC` 是 Google Fonts 可加载、跨平台渲染一致的最优解；国内网络环境需考虑 fallback 到系统中文字体（PingFang/微软雅黑），字体栈已覆盖
4. **JetBrains Mono 是本产品的差异化细节**：法规标准号（`JGJ 59-2011`）、条款号（`3.13.3`）、文档编号全部用等宽渲染——像工程图纸上的编号标注，一行内对齐、可扫读、零歧义（`1` vs `l`、`0` vs `O` 在条款号里是真实风险）

**字号阶梯（固定 rem，Product 寄存器 1.125–1.2 步进）：**

| 层级 | 值 | 用途 |
|------|-----|------|
| `--text-xs` | 0.75rem (12px) | 徽章、时间戳、免责声明 |
| `--text-sm` | 0.875rem (14px) | 辅助说明、引用卡片元信息 |
| `--text-base` | 1rem (16px) | **聊天正文基准**（法规条文阅读，不小于此值） |
| `--text-lg` | 1.125rem (18px) | 回答内小节标题 |
| `--text-xl` | 1.25rem (24px) | 欢迎态主标题辅行 |
| `--text-2xl` | 1.5rem (24→48px 级，取 24px) | 欢迎态主标题 |
| `--text-3xl` | 1.875rem (30px) | 仅欢迎态大标题（单屏一次） |

**字距规则**：正文 0 / 小字（12-13px 辅助）+0.01em / 中文标题 -0.01em / ALL CAPS（如 `JGJ 59-2011` 标准号英数段）+0.06em。

**字重三级**：400 正文（法规条文用 400，绝不用粗体堆砌——公文排版习惯）/ 510 按钮与小节标题 / 590 页面级标题。

**行高**：聊天正文 1.75（法规条文长句多，比常规 1.5 更宽松）/ 标题 1.25 / 等宽编号块 1.6。

### 4.3 圆角 / 间距 / 阴影

| 维度 | 取值 | 理由 |
|------|------|------|
| 卡片圆角 | `--radius-lg: 12px` | Product 寄存器克制值，政务工具不夸张圆滑（上限 12–16px 红线内） |
| 按钮/输入框 | `--radius-md: 8px` | 标准控件 |
| 引用 chip / 徽章 | `--radius-sm: 6px` | 小元素 |
| 头像/计数气泡 | `--radius-full: 9999px` | 圆形 |
| 间距基准 | 4px 网格：4/8/12/16/20/24/32/48 | 消息间距 24px、气泡内边距 16px、区块间距 32px |
| 阴影 | `--elev-raised: 0 1px 2px rgba(15,23,42,0.04), 0 4px 12px rgba(15,23,42,0.06)` | 低强度、带 slate 蓝调的阴影（非纯黑）；主要靠 1px 边框分层（"文件感"），阴影仅用于浮层（弹层/抽屉） |
| 分层策略 | 静态卡片 = `1px solid var(--border)`，无阴影；浮层 = 边框 + `--elev-raised` | 政务工具的"纸面文件"质感，拒绝漂浮卡片堆 |

### 4.4 图标库选型建议 — Lucide

**建议锁定 Lucide（最终由架构师在 Spec 确认），证据链：**

| 评估项 | Lucide 表现 |

| 图标量 | 1500+（Feather 的社区续作，280→1500+ 扩充） |

| 一致性 | 手工策展集合，视觉漂移近乎为零（对比 Tabler 5900+ 的偶发粗细不一） |

**建筑安全场景的关键语义图标全部齐备（本项目核心图标映射草案）：**

| 场景 | Lucide 图标 | 尺寸 |

## 6. 关键交互设计（本产品差异化的三件事）

### 6.1 法规引用卡片（核心差异化组件）

**三层渐进披露（ChatGPT 模式裁剪为两层半）：**

**第 1 层 — 内联引用 chip（句子级，阅读流内）：**

```
正文句子 [1] ————— 后续句子 [2][3]
```
- 样式：20×20px 圆角小方块（`--radius-sm`），`--accent-subtle` 底 + `--accent` 文字，上标位置附于句末标点前
- hover/focus：弹出预览卡（法规名 + 条款号 + 摘要首行 2 行截断）
- 移动端：点击直接打开第 3 层面板（跳过预览，减少层级）
- 同一来源多条款引用：chip 合并为 `[1]×3` 计数格式，展开显示 3 个条款

**第 2 层 — 引用来源卡片行（回答底部）：**

```
引用来源 · 命中 3 份法规
┌────────────────────┐ ┌────────────────────┐ ┌────────────────────┐
│ [file-text]         │ │ [file-text]         │ │ [file-text]         │
│ 建筑施工高处作业安全… │ │ 建筑施工安全检查标准  │ │ 建筑与市政工程施工…  │
│ JGJ 80-2016 (mono)  │ │ JGJ 59-2011 (mono)  │ │ GB 55034-2022(mono) │
│ 第4.1.1条 · 第4.3.1条│ │ 第3.13.3条           │ │ 第3.2.3条 [强制]    │
└────────────────────┘ └────────────────────┘ └────────────────────┘
```
- 卡片：`--surface` 底 + `1px --border` 边框 + 12px 圆角，hover 边框转 `--accent`
- 信息结构：法规图标（16px）+ 法规全名（1 行截断）+ 标准号（**mono 字体**）+ 命中条款号列表
- `[强制]` 徽章：`--warn-subtle` 底 + `--warn` 文字 + `octagon-alert` 12px 图标——**强制性条文（如 GB 55034 全文强制规范）是建筑行业的真实分级知识，此徽章是产品专业度的信号弹**
- 卡片行可横向滚动（>3 张时），末尾"查看全部 N 处引用"入口

**第 3 层 — 原文片段面板（点击卡片/chip 展开）：**

- 桌面右侧滑入 420px / 移动底部抽屉 75vh
- 内容自上而下：法规全名（510 字重）→ 标准号+发文机构+年份（sm, muted, mono 标准号）→ 状态徽章（现行有效）→ **条款原文块**（`--surface-warm` 底 + 左侧 3px `--accent` 引用条——注：这是引用块的"块引用"语义用法，非卡片装饰性侧条纹）→ **命中句高亮**（`--warn-subtle` 底 + `--fg` 文字，黄底黑字，工程图纸批注感）
- 底部操作：「复制条款」「查看完整文档」（P1 深链到知识库浏览页锚点）

### 6.2 回答生成 Loading 状态

**分阶段过程指示（Perplexity "Completed N steps" 的政务版）+ 流式渲染：**

```
┌─ AI 头像 ──────────────────────────┐
│ [sparkles] 正在检索法规库…            │ ← 阶段1（检索中，0.5-2s）
│   已检索 34 份法规 · 命中 5 处条款     │ ← 阶段2（检索完成，逐条累加计数）
│ [sparkles] 正在组织回答…             │ ← 阶段3（生成中）
│ ▂▂▂▂▁▁▂▂▂▁ （骨架占位或流式文字）    │
│                        [停止按钮]    │
└───────────────────────────────────┘
```

- **阶段语言用用户心智模型**（"检索法规库"而非"向量检索 Top-K 重排"）
- 阶段 2 的命中计数（"命中 5 处条款"）是信任建立的黄金 1.5 秒——把 RAG 的检索行为显性化
- 生成中：流式逐 token 渲染（文字渐进出现，无打字机音效），同时"停止"按钮常驻（AbortController 模式）
- 全程时长预期管理：>3s 才显示阶段文案，<3s 静默流畅直出（避免闪烁感）
- `prefers-reduced-motion`：流式渲染改为整段淡入（200ms 一次）

### 6.3 检索命中 / 未命中状态

**命中态（正常路径）：**
- 回答顶部（或引用行）显示 `check-circle-2` 16px + "基于 3 份法规 · 5 处条款"（sm, success 色仅图标）
- 引用卡片区正常呈现（见 6.1）

**部分命中（低置信，score < 阈值）：**
- 回答前置提示条：`circle-alert` + "以下回答基于相关度较低的条款，请核对原文"（`--warn-subtle` 底 + `#92400E` 文字）
- 引用卡片照常显示，但显示相关度提示

**未命中态（知识库外/无相关条款）：**

```
┌─ AI 头像 ──────────────────────────┐
│ [search-x 20px, danger]            │
│ 知识库中未找到与该问题直接相关的条款    │
│                                    │
│ 可能的原因：                        │
│ · 问题涉及法规知识库（34 份）之外的内容 │
│ · 表述过于口语化，试试使用规范术语     │
│                                    │
│ 建议尝试：                          │
│ [临边防护栏杆高度要求] [脚手架验收标准] │  ← 相关高频问题 chip
│                                    │
│ [重新表述] [换个问题问]               │
└───────────────────────────────────┘
```

- **绝不编造**：未命中时明确说"未找到"，并给出引导（这是政务产品的诚信底线）
- 不用红色大标题恐吓，用结构化引导（原因 + 建议 + 行动）

**免责声明（政务合规必备，每个回答底部固定微字）：**

> 本回答由 AI 基于知识库收录的法规文本生成，仅供参考。正式执行请以官方发布的现行有效版本为准。

- `--text-xs` + `--meta` 色，回答操作行下方，视觉极轻但必须存在

### 6.4 状态矩阵总表（聊天主流程 5 态）

| 状态 | 呈现 |
|------|------|
| Loading | §6.2 分阶段过程指示 + 流式渲染 + 停止按钮 |
| Empty | §5.2 欢迎态（示例问题卡片 + 知识库规模） |

- 引用卡片行移动端横向滚动（`scroll-snap`），触摸目标 ≥44×44px
- 法规长表格/条款块允许横向滚动，禁止整页横向滚动

**无障碍：**
- 全部文本对比度 ≥4.5:1（本方案色值已校验，见 §4.1 表）
- 引用 chip：`<button aria-label="查看引用 1：建筑施工高处作业安全技术规范 JGJ 80-2016 第 4.1.1 条">`，键盘 Tab 可达，Enter 打开
- 引用预览：focus 与 click 均可触发（非仅 hover——移动端无 hover）
- 颜色之外必须有文本等价物：`[强制]` 徽章有文字；命中态有文字计数
- `prefers-reduced-motion`：流式渲染→整段淡入；抽屉滑动→直接显示
- 加载阶段切换用 `aria-live="polite"` 播报
