# 3.3 时效状态进上下文 · 实测结论报告

> 执行：2026-11-04（上下文改进计划第 3 期第 1 项）｜本地实例 `127.0.0.1:9001`（37 份 / 509 块，含 0080）
> 结论：**改动落地，生成侧补齐时效状态；状态类问题从「拒答/无法判断」变为可正确作答；62 题同 KB A/B 零回归**

---

## 一、复现问题（改前基线）

`docs_meta.json` 的 `valid_status` 核定结论经 ADR-006 只作用于**检索侧降权 + 前端徽章**；
`_sources_payload` 虽带 `validStatus`，但 `llm.stream_chat` 拼的片段头只有
`《标题》条款（页码）`——**LLM 从来看不到时效状态**。

改前 4 题专项（`eval_val-before_20261104.json`，`fact_all_ok 2/4`）：

| 题 | 改前答案 |
|---|---|
| VAL-01 指南生效了吗 | 「片段中没有关于其生效状态或施行日期的规定……无法据此判断其是否生效」 |
| VAL-02 两版本以哪个为准 | 整题拒答「知识库中未找到与该问题直接相关的条款」 |
| VAL-03 缺陷清单是否现行 | 答「试行」但补一句「无法判断其当前是否仍然有效，建议查阅发布机关公告」 |
| VAL-04 规定现在还有效吗 | 整题拒答 |

A/B 探针（`tests/poc_validity_gen.py` 手工把 0069/0070/0078 同装进上下文，
绕开检索降权）改前回答：**「无法判断施工应以征求意见稿还是试行版为准……
建议向发布机关咨询」**——检索侧早已核定，生成侧却把两个版本平等对待。

## 二、改动（app/llm.py）

片段头追加〔状态〕行，词表与 ADR-006 增补版 / 前端徽章同一口径：

| `valid_status` | 标注 |
|---|---|
| `effective` | 〔状态：现行有效〕 |
| `trial` | 〔状态：试行，已印发施行，现行有效〕 |
| `consultation` | 〔状态：征求意见稿，未生效，不得作为现行施工依据〕 |
| `repealed` | 〔状态：已废止，不得作为现行依据〕 |
| `na` / `unknown` / 空 | **不标注**（沿用 ADR-006「未核定不动作」；11 份 unknown 若标「待确认」会诱发 hedging，A7/A8/C3 依据文档恰在其中） |

实现为纯函数 `build_context()`；有标注时片段块前加一行说明（〔状态〕属于片段内容、
可据此回答时效与版本取舍、多版本以现行/试行有效为准）。**契约规则 1~6 与逐字引用
机制逐字未动**，`prompts.py` 零改动；未核定语料零标注时输出与历史版本逐字节一致。

## 三、A/B 结果

### 1. 探针（两版本同处上下文）——决定性证据

> 改前：无法判断施工应以征求意见稿还是试行版为准……建议向发布机关咨询
> 改后：**应以试行版为准，征求意见稿未生效，不得作为现行施工依据**，并分别引用 [1][2] 标注两版状态

证据：`docs/eval/results/val_ab_probe_before.txt` / `val_ab_probe_after.txt`

### 2. 专项 4 题（`docs/eval/eval_set_validity.json`）

| 题 | 改前 | 改后稳定守卫 | 说明 |
|---|---|---|---|
| VAL-01 试行版状态 | 2/4 全局基线中勉强 OK（含 hedge） | **3/3 稳定 OK**，直接答「试行，已印发施行，现行有效」 | 稳定守卫 |
| VAL-03 0071 试行状态 | 同上有 hedge | **3/3 稳定 OK** | 稳定守卫 |
| VAL-04 0078 现行有效 | 拒答 | **3/3 稳定 OK**，甚至主动区分附录里的旧《暂行规定》 | 稳定守卫 |
| VAL-02 两版本取舍 | 拒答 | **抖动观察题**：v2 说明行 0/3 通过（曾有一次 4/4）；v3 澄清后 2/3 通过 | 见下 |

**VAL-02 为何抖动**：0070 经 ×0.15 降权后进不了 top-8，问题又问「两版本区别」，
LLM 在「按〔状态〕+版本取舍规则作答」与「按契约规则 4 拒答」之间摆。两种行为都
符合契约（拒答诚实、作答有据），故列为**观察题而非硬门**；`fact_all_ok` 在该集上
本次为 3/4，跨多次运行区间 3/4~4/4。真正的「未生效不得作为依据」由探针 A/B 与
`tests/validity_ctx_test.py` 硬守卫，不依赖这题。

### 3. 62 题全量 · 同 KB 改前/改后 A/B（关键验收）

> **混杂因素排除**：11-03 基线跑的是**线上** 47.109.98.111:9000（34 份 / 414 块），
> 本机是 37 份 / 509 块（0080 GB 55034 入库后）。两边 KB 不同不可直接比。
> 故用 `git stash` 暂存改动，在**同一台、同一 KB** 上跑改前对照组 `ctx-control-pre2`。

| 指标 | 改前 `ctx-control-pre2` | 改后 v2 `ctx-validity` | 改后 v3 `ctx-validity-v3` |
|---|---|---|---|
| retrieval_hit3 | 51/54 | 51/54 | 51/54 |
| ctx_hit | 54/54 | 54/54 | 54/54 |
| ctx_block_hit | 49/54 | 49/54 | 49/54 |
| answer_full_cov | 47/54 | 47/54 | 47/54 |
| **fact_all_ok** | **45/54** | **45/54** | **45/54** |
| citation_rate | 52/54 | 51/54 | 51/54 |

| boundary_pass | 3/3 | 2/3 | 2/3 |

**逐题 ok 对比：改前 ↔ 改后（v2、v3）零互换**——同一批 9 题失败、同一批 45 题通过。
即 3.3 对 62 题**零回归**；`45/54` 是本机 509 块 KB 的新基线，改前改后都这个数。

**边界题 2/3 是打分口径假象**：EDGE-05 改前整题拒答（含「未找到」→ 自动 PASS），
改后 3/3 复测稳定给出更可用的**部分可溯源答案**——「未给出/未列出具体技术指标数值」
+ 引用 [9][3]（应符合 GB 2811 / 每名救援人员 1 个安全帽）+ 建议查标准原文。语义上
已明示未收录，无编造，人工复核判 PASS；`run_eval.score_edge` 的 `BOUNDARY_OK` 词表
未收录「未给出/未列出」类措辞故标 REVIEW。是否扩充词表属评测器小修，本次不动
（避免为改分而改分）。

## 四、口径漂移与新发现（需单独决策）

1. **硬门需按 KB 重新定标**：改进计划写死 `fact_all_ok ≥ 51/55`，那是线上 414 块 KB
   的口径；本机 509 块 KB 实测 45/54（改前改后一致）。`51/54 → 45/54` 的净 -6 与
   3.3 无关，是 0080 入库后同主题文档挤占上下文排位所致，即 OPEN-DECISIONS 已登记的
   「知识库扩充后同主题排序精化」OPEN 项。逐题看，掉的多是「答案块没进 top-14」类
   （DEF-04 氧气浓度块、SAF-08 36V 块、PM-08 1 小时块、GOV-06 场景判定块）。
2. **线上仍是改前版本**：47.109.98.111:9000 为 34 份 / 414 块且无本次改动；上线需单独
   发版（部署后应重跑一次线上 62 题定标）。
3. **VAL-04 原问法**（「什么时候施行的」）是已知检索边界：施行日期块（0078 第22条）
   排窗口 15+ 位进不了上下文，LLM 诚实拒答；已改为状态题，原问法记录在评测集 note 中。

## 五、结论与后续

- 3.3 **验收通过**：生成侧时效对齐落地，状态类问题可正确作答，未生效文件在两版本
  同处上下文时被明确排除；零回归证据为同 KB 逐题零互换。
- 后续优先：① 2.4 改写词对齐（第 2 期唯一保留项）；② 3.1 相邻条款定向注入；
  ③ 4.1 文档图上下文（母通知-附件关系，检索命中 0069 自动带出 0070 时效对照，
  这才是「跨版本对照」的正解）；④ 0080 排序精化 POC（硬门重新定标）。
