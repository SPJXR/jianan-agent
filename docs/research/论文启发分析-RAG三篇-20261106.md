## 二、逐篇启发

### 论文 3 优先讲：Agentic RAG（启发最直接、可落地）

#### 核心结果

| 设置 | Qwen3-4B | Fanar-2-27B |
|------|---------|------------|
| Base | 21.85 | 48.65 |
| +RAG | 38.85 | 51.50 |
| **+Agentic RAG** | **48.90（+10.05）** | **57.30（+5.80）** |

- 错误恢复分析（Table 5）：Agentic 救回 36 例，其中 **24 例是「未尝试→正确」、12 例是「错误→正确」**——迭代证据搜寻的第一收益是**减少过度弃答**（把 standard RAG 检索一次不中就放弃的问题救回来），其次才是纠正错误
- 代价（Table 6）：平均 tokens 502→1520（×3）、tool calls 0→6、**延迟 0.52s→3.45s（×6.63）**
- 工具集：semantic search / surah metadata / direct verse reading / within-surah search 四个结构化工具，模型 plan→invoke→inspect→iterate

#### 对项目的映射

1. **与 OPEN 项「排序精化」的关系**：扩库后 GOV-06/DEF-04 类问题 top3 被跨部门手册占位，现有候选（按问题分组加权、多来源并列引用）都是**排序层微调**。本文提供了第三候选：**歧义场景升级为 agentic 证据迭代**——LLM 用工具自主消歧（读文档元信息、直读候选块、重检索），把「排序该谁在前」转化为「让模型自己收集证据后裁决」。这同时是收口 OPEN 项与第 4 期研究向的合流点。
2. **工具集几乎零成本可得**：项目已有全部原子能力——`hybrid_search`（semantic search）、`docs_meta`/时效台账（metadata retrieval）、`get_chunk_context`（direct reading）。**缺的只是工具调用编排层**，不需要新基础设施。
3. **延迟预算决定了不能全量 agentic**：产品约束 P95<800ms（现场即时问答），×6.63 的延迟不可接受。落地方案是项目一贯的**条件触发哲学**（ADR-002/006 同款）：仅当「弱命中 + 两阶段改写后 top_cov 仍不达标」时升级 agentic 循环（限步 N=2~3），预计只影响 <10% 的问题，其余保持现有毫秒级链路。综述 §3.3.2 的 Adaptive-RAG（评估复杂度决定是否触发检索）正是这一模式的学名。
4. **评测维度直接借用**：citation fidelity（引用保真）、abstention rate（弃答率）+ **过度弃答**（not_attempted 但应答）——项目 62 题已有拒答组（正确拒答 5/5），可补「过度弃答率」指标：检索其实有答案但系统放弃的比例（GOV-07 历史案例就是此类）。
5. **LLM-as-judge 的教训**：他们实测人工-LLM 一致率 79%、标注者间 Cohen's κ 仅 0.51。项目评测目前用**规则断言**（逐字引用比对、编号白名单）——这反而是优势，毕设可论证「规则断言先于 LLM judge」的设计选择；若未来引入 LLM judge，必须先做 judge 校准协议（held-out 子集 + 一致率报告）。

### 论文 2：综述（定位、自证与具体技术候选）

#### 对项目最有价值的四点

**A. 给 10 个 ADR 找到学术坐标系**（毕设「相关工作」直接可用）：

| 综述分类（§3） | 项目对应实现 |
|---------------|-------------|
| 3.1.2 查询增强（改写/扩展） | ADR-010 多轮指代解析改写；ADR-008 口语同义映射表 |
| 3.3.1 多步检索策略 | ADR-007 两阶段检索并集合并 |
| 3.3.2 动态调整（是否触发检索） | ADR-002 条件补充（强命中不走向量）；改进计划若落地「条件触发 agentic」同属此类 |
| 3.4 数据源/索引增强 | ADR-005 表格感知分块；PER_DOC_CAP=4 文档多样性（对应「霸屏抑制」） |
| 3.5.1 重排与过滤 | ADR-004 检索窗口与同文档补位；ADR-006 时效降权 |
| LLM 增强（§4.2，以内强内） | 车蕾论文方向 C（LoRA）的学术定位；项目现行路线是「以外补内」 |
| 知识更新（时效性） | 法规时效核查台账 + ADR-006 + 3.3 时效状态进上下文——比综述讨论的通用方案更完整（检索侧降权 + 生成侧标注双管） |

这张表的价值：证明项目 8 周的工程实践**与 2026 年学术前沿的分类学一致**，且在「知识更新」维度做出了综述所述各方案之外更贴法规场景的组合。

**B. RAG vs 长上下文的实测对照**：综述引 U-NIAH——128K 上下文仍有「中间遗忘」（中间位置准确率降超 20%，U 形曲线）；RAG 在复杂任务胜率 82.58%。项目 POC 顺带发现「上下文长度本身不是瓶颈」（均值 6807 字≈9k tokens，远非 deepseek 窗口压力区，16→14 块截断后无系统性拒答）。这两条不矛盾：**中间遗忘是位置效应不是长度效应**——项目 cite_pos 指标（被引块位次分布）正是度量它的工具，毕设可把「9k tokens 无压力区但仍有位置偏好」作为实测补充，比单纯引用 U-NIAH 更有说服力。

**C. 三个具体技术候选**（按成本-收益排序）：
- **Self-RAG 式自反思**（PopQA 55.8%/PubHealth 73.5%）：生成后自检「引用是否支持结论」，不支持则修订或弃答。项目已有离线 `verify_verbatim.py`（414/414 复算），迁移为**在线轻量自检**（只查答案所引 [n] 编号的块是否真实在上下文中 + 关键结论是否被引文覆盖）成本很低，且与 Agentic 的「answer revision」呼应——这是第 3 期之后生成侧的自然下一步。
- **CtrlA 置信度触发检索**（诚实性引导 + 置信度监测）：项目改写触发目前用固定覆盖率阈值（0.5），2.4 刚修复判据缺陷、62 题稳定，**不建议现在动**；但可登记为「若未来引入生成侧置信度信号」的候选。
- **CRAG 三分类**（correct/incorrect/ambiguous）：强/弱命中二分类升级为三分——ambiguous 触发补充检索。与 OPEN 排序精化 POC 同期评估即可，不单独立项。

**D. 综述局限性(1) 的差异化叙事**：综述指出一般 RAG 的关键缺陷——「知识库缺乏目标信息时，系统生成看似合理但错误的回答而非明确『未知』」。项目的诚实拒答契约 + 拒答组评测（62 题中 refusal 5/5）+ 0001 下架后正确转拒答，正是对该局限的**工程级完整回应**。毕设问题陈述可直接引此段立论。

### 论文 1：BadRDM（安全面叙事 + 低成本加固）

#### 核心事实
- 投毒比例约 **2×10⁻⁷**（检索库塞极少量代理即可），人工检查不现实；攻击者甚至可只发布特征向量
- 防御实验（Table 3）：**UFID**（扰动查询 + 生成分析检测可疑查询）最有效（ASR 0.9643→0.4048）；微调类（BFT/CleanCLIP/Unlearning）收效有限（0.80~0.90）；TextPerturb 几乎无效
- 结论：需要更安全的机制——检索库完整性是 RAG 系统的信任根基

#### 对项目的映射（文本 RAG 迁移）

1. **威胁模型显式化**：项目知识库管道本身就是供应链——`ingest_web.py` 抓网页（曾遇「相关推荐」栏污染）、0080 从防盗版切片 PDF OCR（曾拼漏 2/8 切片）、.doc 走 COM 转换。BadRDM 证明：**极少量被操纵内容就能系统性扭曲「检索到什么」进而扭曲「引用什么」**——而项目的逐字引用契约恰好把最终防线交给了用户（引用可点击核查原文），这个设计选择现在有了学术依据支撑。
2. **低成本加固清单**（一次迭代可全部做完）：
   - 入库审计：每块来源域名分布统计 + 非白名单来源告警（web_sources.json 已有台账，缺监控视图）
   - 索引完整性：启动时校验 vec_index 与 kb.sqlite 的 chunk_id 对齐 + chunks_snapshot 哈希比对（自检逻辑已有，升级为服务启动时执行并落 health）
   - 异常命中检测（UFID 思路的轻量版）：同一低相关块高频跨题命中 → 可疑（PER_DOC_CAP=4 已是霸屏抑制雏形，可加跨题统计）
3. **毕设写作价值**：答辩时「你的知识库内容可信吗」是必考题。引用 ACL 2026 的 BadRDM 说明检索增强安全是前沿关注面，再展示自己的完整性设计（来源台账/哈希/逐字引用/时效核定四层），是把潜在弱点转化为加分项的素材。
