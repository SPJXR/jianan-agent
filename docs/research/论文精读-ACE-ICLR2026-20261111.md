## 一、一句话与速览

**一句话**：不改权重，把上下文当作**持续演化的 playbook**——用 Generator（带上下文执行）、Reflector（从执行轨迹提炼教训）、Curator（合成紧凑 delta、用**非 LLM 确定性逻辑**合并）三模块做**增量更新**，对抗现有上下文优化方法的两大失败模式（brevity bias / context collapse），在 AppWorld 与金融基准上以更低成本稳定超越 ICL / MIPROv2 / GEPA / Dynamic Cheatsheet。

| 维度 | 数字 |
|------|------|
| AppWorld（DeepSeek-V3.1-671B） | 基线 42.4 → **59.4（offline，+17.0）/ 59.5（online 无 GT，+17.1）**；GEPA 仅 46.4、DC 51.9 |
| 金融（FiNER+Formula） | 69.1 → **81.9（offline，+12.8）**；GEPA 72.5 |
| 排行榜 | AppWorld 平均与榜首 IBM CUGA（60.3，GPT-4.1）持平；**test-challenge 反超 8.4% TGC**，用的是更小开源模型 |
| 效率 | 比 GEPA 延迟 −82.3%、rollouts −75.1%；比 DC 在线延迟 −91.5%、token 成本 −83.6%；GPT-5.1 KV cache 命中 91.8%，计费降 82.6% |
| 无标注监督 | AppWorld 无 GT 仍 +14.8~+17.1（靠代码执行成败等**自然执行反馈**）；FiNER 无 GT 时**退化 −3.4**（边界！） |

## 二、深读要点（项目视角挑干的）

### 2.1 两大失败模式——为什么「让 LLM 重写上下文」会失败

- **Brevity bias**：提示词优化器偏爱收敛到「短而泛」的指令，迭代间还会继承 seed 错误。知识密集任务恰恰依赖**累积**细节而非压缩。
- **Context collapse**：让 LLM 每步**整体重写**累积上下文时，上下文一大它就压缩成低信息摘要——论文给出突变案例：18,282 tokens → 122 tokens，准确率 66.7 → 57.1（**比完全不适应还差**）。
- **核心论点**：LLM 与人不同，**长而详细的上下文上表现更好**，能自行蒸馏相关性；上下文应是「全面 playbook」，把「什么重要」的判断留给推理时刻的模型。

### 2.2 框架与算法

- **Context Memory = 条目化 bullets 集合**：每条带 `unique_id / helpful_counter / harmful_counter` 元数据。三性质：定位（只动相关条目）、细粒度检索、增量适应。
- **增量 delta 更新**：从不整体重写。Reflector 从执行轨迹提炼教训（最多 5 轮精炼）→ Curator 合成小 delta → **确定性代码合并**（追加新条目、原地累加计数器、语义 embedding 去重 = Grow-and-Refine）。合并器不是 LLM——**LLM 的压缩倾向无法触碰整体结构**，这是防坍缩的结构性保证。
- **三角色同一模型**（DeepSeek-V3.1 非 thinking）：防止强 Reflector 向弱 Generator 泄漏知识，把贡献隔离在「上下文本身」。
- **offline（训练集优化系统提示词）/ online（测试流上边答边学 agent memory）/ offline warmup + online 组合**（56.1 → 59.5，warmup 值 3.4 点）。

### 2.3 有效性边界（诚实部分，对我们最有用）

- **反馈质量决定一切**：AppWorld/Formula 有执行反馈 → 无 GT 也大涨；FiNER 是标注任务、库内无法自验证 → 无 GT 时 ACE 也退化 −3.4。**上下文演化不能替代外部真值**。
- 简单任务（Game of 24、HotPotQA）未必受益；对噪声反思只优雅退化，全对抗更新才低于基线。
- 消融：Reflector+精炼 ≈4.3 点、multi-epoch ≈2.6 点、warmup ≈3.4 点——**累积与迭代本身就是收益来源**。

## 三、对项目的启示

### 3.1 最先要说的：我们已经在做「手工版 ACE」，而且做对了

这张对照表是本文最重要的一页——**项目 8 周的上下文工程纪律与 ACE 的设计逐条同构**：

| ACE 概念 | 项目对应实现 | 证据 |
|---|---|---|
| Context Memory（条目化、带元数据、可演化） | `docs_meta` 时效台账：每文档 `valid_status` + 人工核定记录 + 前端徽章；ADR/OPEN-DECISIONS（只追加+就地关闭） | ADR-006、3.3 报告 |
| 增量 delta 更新（只加不改、定位编辑） | 3.3 片段头注入〔状态〕行——**有标注才加、零标注路径逐字节一致**；3.1 相邻块**追加**在片段尾部、不进编号体系 | `validity_ctx_test` / `adjacent_ctx_test` 单测守卫 |
| Curator 用确定性代码合并（LLM 压缩倾向触不到结构） | 提示词演化纪律：契约规则 1~6 与 `prompts.py` **逐字锁定**；说明行 v1→v3 每次只动一句话 | 3.3 提交 26b023f |
| Context collapse 的结构性预防 | 「零标注零注入路径输出与历史版本逐字节一致」**机器守卫**——坍缩在 CI 层被拦截 | 单测红线 |
| Reflector 的执行反馈 | 62 题规则断言评测（逐字引用比对、编号白名单、拒答判据）——比论文的自然执行反馈**更可靠** | run_eval + verify_verbatim |
| 长上下文 + KV cache 更优 | 上下文 POC 实测：均值 6807 字 ≈9k tokens 远非压力区；16→14 块截断无系统性拒答 | 2.2 POC 报告 |
| 人工 Reflector/Curator（human-in-the-loop） | 法规时效**人工核定**——恰是 FiNER 反例的正解：库内不可自验证的真值必须外置 | 0001 下架闭环 |

**给毕设的叙事**：ACE 把「上下文要当演化的 playbook、更新必须增量且确定性、演化必须配机器守卫」上升为 ICLR 2026 前沿结论——我们此前凭工程直觉建立的「只加不改契约 + 逐字节一致守卫 + 规则断言反馈」纪律，现在每一条都有学术对应。答辩讲上下文工程方法论时，ACE 是最好的引用支点。

### 3.2 新增启示一：helpful/harmful 计数器 → 用「N 次计数」对抗 LLM 抖动

ACE 的 bullet 元数据设计（有用/有害计数器）不是装饰——它把「单次反馈噪声大」这个问题在数据结构层面解决：**一个 bullet 的去留由累积计数决定，而不是单次评测**。

项目刚吃过这个亏：GOV-06 拒答格式跨日漂移、VAL-02 在 0/3 与 2/3 间摆、MT-02 单次 miss 复测 3/3 过——每次我们都在靠「复测 3 次」的人肉纪律兜底。ACE 给出结构化做法：**任何提示词段（说明行、相邻标注措辞、角色策略段）都应带计数台账**——62 题每次跑完自动统计「该段在场时的题目通过/失败分布」，升降级看累计计数而非单次结果。这可以直接落成 `run_eval` 的一个扩展输出（每题所用提示词段版本已可从 backend/版本号回溯），成本低、且把「复测 3 次」从纪律变成机制。

### 3.3 新增启示二：反馈分层——我们的评测体系天然满足 ACE 的适用条件，但时效核定不满足（这是对的）

- ACE 无 GT 仍能涨的条件是**自然执行反馈**。我们的在线答案恰好有一套**机械可验的反馈**：引用编号是否在 sources 白名单、引文是否逐字、拒答是否走对路径——这是把 P2（在线引用自检，三篇分析已登记）变成**反馈发生器**的理论依据：自检通过/失败信号可以驱动后续任何演化决策。
- 反面映射同样重要：**法规时效（valid_status）永远不该走自动演化**——它对应 FiNER 的「库内不可自验证标注」，ACE 自己证明这条路会退化。人工核定 + ADR-006 双管（检索降权+生成标注）继续是正解，且现在有论文级反面证据支撑这个「不做」。
- 排序精化 OPEN 项同理：候选权重的去留应挂在我们 62 题的规则断言反馈上（同日同批次口径，11-07 已登记），不引入 LLM judge。

### 3.4 新增启示三：ADR-008 同义映射表 = 最适合「ACE 化」的资产

项目里最接近 ACE Context Memory 形态的资产是 **ADR-008 口语同义映射表**（人工维护、条目化、只增不删）。它的演化反馈信号天然存在：**改写后 top_cov 是否提升**（检索层机械可测，无需 GT）。ACE online 模式给出演化路线：

```
生产查询流 → 改写前/后 top_cov 对比
  → 提升 > 阈值：该「问法→术语」映射 helpful+1
  → 未提升/改写引入翻车：harmful+1
  → 累计到阈值才由人工 Curator 决定入表/移除（delta 合并仍确定性）
```

这保持了我们一贯的「机器提议、人裁决、增量入表」哲学，且反馈信号不需要任何标注——**是这个项目里唯一同时满足「ACE 适用条件 + 产品契约（不影响线上延迟，纯离线分析）」的演化点**。可作为第 4 期研究向的第三候选（与 4.1 文档图、条件触发 agentic 并列）。

### 3.5 新增启示四：对前篇 P1（条件触发 agentic）的增强论证

三篇分析里 P1 建议「弱命中+两步不中 → 工具循环」。ACE 补了两个论据：
1. **AppWorld test-challenge 上 ACE 在线 +24.5 TGC**——越难的任务，上下文演化收益越大；我们最难的那批题（GOV-06/DEF-04 类弱命中）恰是候选场景；
2. ACE 的 playbook 里存的是**策略条目**（何时用哪个工具、常见失败模式）——条件触发 agentic 的「循环控制提示词」本身可以做成条目化 playbook，由过度弃答率（P4 指标）反馈演化，而不是手写一次定终身。

### 3.6 一个必要的清醒剂：ACE 的场景不等于我们的场景

- ACE 优化的是** agentic 任务的成功率**（代码执行、工具调用）；我们是**知识问答 + 逐字引用契约**——引用契约的红线（引用必须指向 sources 编号）**不可纳入演化空间**。任何 ACE 化试点必须把可演化面（策略段、映射表）与锁定面（契约规则、拒答判据）显式分离，演化只发生在前者。
- ACE 的 multi-epoch 在训练集上反复迭代；我们的 62 题是**守卫**不是**训练集**——可以用于计数反馈，但绝不能对着 62 题分数直接做提示词搜索（那是评测过拟合，test-integrity 红线）。演化反馈应来自生产查询流（3.4 的 top_cov 信号）或 held-out 扩充题集。

**明确不建议做的**（在 ACE 语境下再次确认）：
- ❌ 用 LLM 整体重写任何提示词/台账（包括「让 DeepSeek 帮我把说明行重写得更好」）——context collapse 的直接触发方式，论文已给出 18K→122 tokens 的突变证据；
- ❌ 对着 62 题分数做自动提示词搜索/演化——评测是守卫不是训练集，过拟合红线；演化反馈源只能是生产查询流的机械信号或 held-out 新题；
- ❌ 时效状态、契约规则、拒答判据纳入任何自动演化空间——对应 FiNER 无 GT 退化教训 + 幻觉红线；
- ❌ 为「长上下文更好」就放弃 14 块截断回退——我们的约束是 LLM 长上下文拒答实测（DEF-04 教训）+ P95 延迟，与 KV cache 论点不冲突但优先级更高。

## 五、一句话总结

ACE 证明了「**上下文是可以自我改进的产品，前提是更新必须增量、合并必须确定性、演化必须有可靠反馈**」——这三个前提我们的项目已经用工程直觉各自做对（逐字节守卫 / 契约锁定 / 规则断言）；它真正带来的新东西是**把「抖动治理」从复测纪律升级为计数台账**、**把同义映射表指认为最安全的演化资产**、以及**给时效人工核定提供了反面证据级的不做理由**。
