## 一、一句话与速览

**一句话**：长上下文三大挑战（成本/性能/位置偏差）源于**关键信息的密度与位置**——用「问题感知」统领四组件：反向条件困惑度选文档（r_k）→ 重排（重要文档置前抗中间遗忘）→ 对比困惑度 token 剪枝 → 子序列恢复实体，2x-6x 压缩下性能反升且位置偏差几乎消失。

| 维度 | 数字 |
|------|------|
| 性能反升 | NQ 2x 压缩 GT 在第 10 位：54.1 → 70.8（相对 **+21.4%**），token 省 4x |
| 位置偏差 | 原始 prompt 中间位置损失 **20+ 分**；压缩+重排后各位置 70.5~77.2 几乎抹平 |
| 消融排序 | 粗粒度问题感知 **≫** 其余全部（去掉 -35 分；LongBench Synth 53.0→18.0） |
| 反面教材 | 无问题感知的 LLMLingua 熵压缩在 NQ **低于 zero-shot** |
| 延迟/成本 | ~10k tokens 2x-6x：端到端 1.4x-2.6x；LooGLE 30k 成本 ↓94% |

## 二、深读要点（项目视角挑干的）

1. **r_k 评分的巧妙**：不算 p(文档|问题)（噪声大），算**问题在文档条件下的困惑度**（加一句 restrict 声明抑制小 LM 幻觉）——数学上 ∝ 条件点互信息。问题感知是整个框架的灵魂，消融贡献是其余组件之和的量级。
2. **重排对所有基线有效**：BM25/嵌入检索选出的文档按重要度重排都有收益，且不伤时间线任务——**便宜、正交、可移植**的一步。
3. **token 级细节**：普通困惑度区分不了关键 token，必须用**对比困惑度**（= 条件 PMI）；压缩预算按文档相关度动态分配。子序列恢复承认「LLM 复制 prompt 实体、token 压缩会损坏实体」——压缩家族自己给出了不压缩的理由。
4. **局限诚实**：问题感知无法缓存（计算 ×2）；复杂多跳关系下感知可能失效。

## 三、对项目的启示（含自有数据实证）

### 3.1 位置偏差：论文的主张在我们数据里直接验证了

用 62 题两轮结果做「被引块位次（[n] 编号即位次）vs 综合通过率」分桶（本日只读自查，可复算）：

| 桶（答案所引最高位次） | ctx-24 通过率 | ctx-31 通过率 | LongLLMLingua 对照 |
|---|---|---|---|
| 1-3 位 | 20/21 | 19/20 | 1st=75.7（最好） |
| 4-8 位 | 20/23 | 20/22 | 中段 |
| **9+ 位（补位区）** | **6/9** | **9/10** | 10th=54.1（−20 分） |

三个结论：
- **位置效应真实存在**：9+ 位桶在 ctx-24 恰是 miss 集中区（PM-06/PM-11 的答案块都在补位区）；被引位次分布约 72% 落在 1-3 位，模型自己也偏好头部。
- **我们的装配已是「重排」的朴素形态**：`hits` 按检索分数降序、primary 8 + 同文档补位 6——与论文「按 r_k 降序重排、指令与问题固定两端」结构同构，且**没花一分钱**。论文「重排对所有基线有效」佐证这个设计选择。
- **cite_pos_dist 从「观察指标」升格为「位置偏差监测器」**：论文证明位置敏感度抹平是可验证目标，我们的 62 题每次跑都免费产出该指标——毕设可直接给「位置效应的工程级实证」。

### 3.2 0080 排序精化 OPEN 项的新候选：r_k 重排

论文最大贡献组件（粗粒度问题感知选择，消融 -35 分）在我们系统里的对应物是 hybrid_search 的词面 BM25——但**排序精化**可以考虑 r_k 思路：对 primary+supplement 14 块用小 LM 算 p(问题|块) 重排，把补位区的答案块（PM-06 型 rank-9）提前。**必须标注的约束**：
- 延迟：小 LM 逐块前向在 P95<800ms 内能否放下需 POC（CPU 推理 14 块是风险点）；
- 词面近似版（BM25 词面重叠作为 r_k 替身）零延迟但与现排序高度相关、预期增量有限；
- 登记为 0080 POC 的**第三候选**（前两候选：来源权威度/角色加权、条件触发 agentic），不单独立项。

### 3.3 2.2 否决的第三条学术对应：熵压缩崩溃案例

LLMLingua（纯信息熵、无问题感知）在 NQ 上**低于 zero-shot**——因为保留大量无关噪声。至此「压缩三重证据链」完整：

| 论文 | 失败模式 | 我们的对应否决 |
|---|---|---|
| RECOMP | 机械截断伤 86% 被引块 | 2.2 POC（截断） |
| LongLLMLingua | 无问题感知的熵压缩崩溃 | 2.2（同源） |
| RECOMP | abstractive 33% 不忠实 | 逐字引用契约 |

**只有任务感知的选择有效**——我们检索层的问题感知（BM25 词面+两阶段改写）正是这一论断的工程实现。

### 3.4 逐字引用契约 vs 压缩家族：又一个「不做」的完整论证

- token 剪枝与逐字契约**根本冲突**（条款一个字不能少，子序列恢复恰恰证明压缩会损实体）；
- 成本动机不成立：论文省的是 GPT-3.5 时代 4k 上下文的钱（NQ ↓71.7%），我们 9k tokens 非压力区、DeepSeek 成本可忽略；
- 延迟动机不成立：1.4x-2.6x 加速的前提是 10k+ tokens 的 prefill 主导，我们的瓶颈在生成不在 prefill。
- 与 RECOMP 增补红线一致：这条「不做」现在有**两篇 ACL/ICLR 论文背书**。

### 3.5 问题感知 vs 缓存的权衡：我们早已做了条件分层

论文自述局限：问题感知无法缓存（×2 计算）。我们的架构恰好在这个权衡上做了分层——**强命中走纯 BM25 词面**（倒排索引天然可缓存、零 LLM 开销），**弱命中才触发改写+向量**（问题感知的强形态，只在 <10% 请求上付费）。ADR-002 的条件触发哲学在「感知强度 vs 延迟」维度又多一个学术注脚。
