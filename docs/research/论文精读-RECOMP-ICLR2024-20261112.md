## 一、一句话与速览

**一句话**：检索文档 prepend 前先压缩成摘要——用**下游 LM 的 end-task 信号**训练压缩器（不是训练「给人看的通用摘要」），检索无帮助时输出**空字符串**实现选择性增强；Top-5 文档压到约 5% token，EM 仅掉 2~4 点。

| 维度 | 数字 |
|------|------|
| 压缩率 | NQ/TQA 保留约 **5% token**（660→36），EM −2.35/−3.69；HotpotQA 11%（EM −2.40） |
| Oracle 天花板 | 句子级 oracle 比完整 Top-5 高 **+20.8 / +16.9 / +9.0 EM**——「选对内容」远胜「给更多」 |
| 无关上下文危害 | 证据无答案时错误复制率：完整 Top-5 **81%** → RECOMP **39%** |
| 保真度 | 抽象式 HotpotQA **33% 摘要完全不忠实**；训练未显式优化 faithfulness |
| 迁移 | LM 任务可跨模型迁移；QA 迁移 LLaMA-13B 在多跳场景明显变弱 |

## 二、对项目的启示

### 2.1 最重要的对照：我们的 2.2 POC 否决 vs RECOMP——否的不是「压缩」，是「机械截断」

RECOMP 与我们 2.2 POC（低分块文本截断，86% 被引块会被截伤 → 否决）表面冲突，实则互补：

| | 我们的 2.2 | RECOMP |
|---|---|---|
| 选择依据 | 检索分数阈值（机械） | **下游 LM end-task 信号**（任务驱动） |
| 粒度 | 块内截断（破坏条款完整性） | 跨文档**选句**（句子完整、可去语境化） |
| 保真 | 截断破坏逐字引用 | extractive 保真 / abstractive 有漂移 |
| 结论 | 否决 | 有效但需训练 |

**启示**：2.2 否决的是「按长度/分数机械砍」，不是「内容选择」本身。RECOMP 的 Oracle 数据（选对句子 +20 EM）说明内容级选择的上限很高——但这需要任务信号训练，不能直接套成「把低分块砍短」。毕设可把这段写成「压缩的两种范式对照实验」：我们实测否定了机械范式，RECOMP 证明了任务信号范式。

### 2.2 逐字引用契约的学术定位：extractive 保真红线

RECOMP 的 abstractive 压缩器在 HotpotQA 上 **33% 摘要完全不忠实**——法规条款里一个数字、一个否定词、一个时效状语的漂移就是错误答案。这给我们的契约一个清晰的学术坐标：

- **我们的「引用必须逐字指向 sources 原文」= extractive 保真原则的极端形式**（不压缩、不转述、可机判）；
- 未来若做任何上下文压缩（例如长文档场景），红线必须是：**只许选句不许改写，引用仍指向原文块，过 verify_verbatim**；abstractive 进不了我们的引用链。

### 2.3 选择性增强 = 我们条件触发哲学的摘要层版本

RECOMP「无帮助则空摘要」与项目既有设计同构：ADR-002 强命中不走向量、改写仅弱命中触发、覆盖率不达标走兜底。它的**错误复制率数据（81%→39%）**还提示了一个我们没量过的维度：**上下文里无关块会诱导模型复制错误内容**——这与 GOV-06 类「上下文有块但答非所问/拒答」的现象同源。评测侧可补一个轻量指标（见行动表）。

### 2.4 效率观的校准：论文没测延迟，我们测过「长度不是瓶颈」

RECOMP 全程用 token 数当效率代理，**未报告延迟/压缩器开销**；110M/775M 压缩器的推理成本没进账。我们实测相反方向：9k tokens 远非 DeepSeek 压力区（2.2 POC），P95<800ms 产品契约下**根本没有给压缩器留预算**。两条证据合起来：RECOMP 的动机（长文档贵）在我们当前规模不成立——**不引入压缩器是正确决策，且有双向证据**。

### 2.5 与 ADR-011 的合流：end-task 信号 = 我们的规则断言反馈

RECOMP 训练压缩器用 QA 的 Exact Match 作信号；我们的 62 题规则断言（关键词覆盖+引用规范+逐字校验）正是同类机械信号。差别在规模：RECOMP 训练集 4 万+样本，我们 62 题——**只够做反馈/计数（ADR-011），不够训练压缩器**。这从数据规模上再次封死「训练压缩器」选项，同时说明台账反馈路线是当前唯一可走的。

## 三、行动建议

| 优先级 | 事项 | 来源 | 成本 | 预期收益 |
|--------|------|------|------|---------|
| P4 期候选④ | **「证据无关时错误复制率」评测补充**：对拒答/边界组统计答案是否从无关上下文复制断言（对照 RECOMP 81%→39% 指标） | §2.3 | 低（规则断言扩展） | 补一个我们没量过的幻觉维度 |
| 登记 | **压缩设计红线**（若未来长文档场景需要）：只许 extractive 选句、引用指向原文块、过逐字校验；禁止 abstractive 进引用链 | §2.2 | 写入 ADR-011 增补或未来 ADR | 防患于未然 |
| P5+ | **毕设素材**：2.2 否决 vs RECOMP 的「机械截断 vs 任务信号压缩」对照；逐字契约=extractive 保真极端形式；Oracle「选择>更多」论证支撑排序精化方向 | §2.1/2.2 | 写作 | 学术叙事完整性 |

**明确不建议做的**：
- ❌ 训练 RECOMP 式压缩器——数据（62 vs 4 万+）、GPU、P95 延迟预算三不足，且我们实测长度非瓶颈；
- ❌ 把 abstractive 摘要引入上下文——33% 不忠实直接违反逐字引用契约；
- ❌ 把 2.2 否决「翻案」成机械截断——RECOMP 恰恰证明机械截断与任务信号压缩是两回事，我们的否决仍然成立；
- ❌ 为「Oracle 上限高」就在装配层加句子级抽取——那属于排序精化 POC 的候选之一，需先 POC 证明不断上下文，不单独立项。

## 四、一句话总结

RECOMP 证明了「**压缩要用任务信号、保真只能走 extractive、无帮助就该不增强**」——这三条分别对应我们项目的「2.2 否决的正确性边界、逐字引用契约的学术坐标、条件触发哲学的摘要层印证」；它对我们最大的价值不是引入压缩（规模与延迟都不允许），而是**把已有工程决策的学术依据补齐，并指出唯一值得补测的新指标：无关上下文诱导的错误复制率**。
