# 建安法规问答助手：上下文处理升级详细计划

制定日期：2026-11-07。
状态：待确认的实施计划。本文件不代表功能已实现、评测已通过或获准上线。
范围：上下文证据组织、适用性、多轮约束、按需补证、评测及与这些改动直接相关的知识库发布检查。

## 1. 目标与当前起点

### 1.1 本轮目标

把“相关片段列表”升级为可追溯、可检查适用范围、能发现证据缺口的证据集合。先让模型、用户和评测看到同一份证据，再考虑增加检索智能。

希望解决的具体问题：

- 模型使用了相邻条款，但引用和评测没有完整记录这些条款。
- 同主题不同领域的文件混在一起，数值或条件不同却被当成同一种规定。
- 目录、选择题选项、说明材料与规范性正文未充分区分。
- 主条款已命中，但定义、条件、例外或附件没有进入上下文。
- 把文档命中、出现关键词和带有引用号误当成答案可靠。
- 弱命中判据无法识别“词面相关，但缺少决定性证据”。

### 1.2 已核对的本机状态

| 项目 | 当前状态 | 使用限制 |
|---|---|---|
| 知识库 | 37份文档、509个片段 | 本机SQLite实查，不代表线上版本 |
| 主链路 | BM25强命中保序；弱命中向量补充、查询改写；召回窗口16 | 不先更换检索模型或融合算法 |
| 上下文 | top-8主证据＋最多6个同文档补位块 | 第一阶段保持候选及排序策略 |
| 相邻补证 | 块尾断裂时补next，最多3块 | 本地未提交实现；仅进模型，不进sources正文 |
| 时效提示 | 已进入模型上下文并已提交 | 不等于已经表达文件性质和适用范围 |
| 多轮 | 最近3轮，改写器取部分历史 | 助手历史不是法规证据 |
| 最新保存主集结果 | 2026-11-06：48/54综合合格，拒答5/5，边界3/3 | 历史保存值，不是本计划的新测结果 |

48/54是旧评分的综合数，不是经过人工语义审核的准确率。SUP-11和GOV-01在保存结果中仅因top-3未命中而不合格；这既不能证明答案错误，也不能未经审核便宣布答案正确。

### 1.3 不做清单

- 不扩充通用知识库，不同时更换LLM、embedding或部署平台。
- 不重启已经被具体POC否决的固定字数截断方案；也不把旧POC扩大成“所有预算控制永远无效”。
- 不默认引入神经重排器、LoRA、图数据库、向量数据库或多智能体框架。
- 不让所有问题进入工具循环，不使用模型自报置信度作为唯一触发依据。
- 不靠历史问题ID、金标关键词或expected_docs在线决定检索路径。
- 不改写历史评测、带日期的研究记录，也不删除已有未提交工作。
- 不把哈希一致、逐字一致或引用编号合法宣传为答案正确的证明。

## 2. 总体架构与实施顺序

目标链路：

```text
当前问题＋已确认的会话约束
          ↓
现有查询改写与条件混合检索
          ↓
证据类型与适用范围检查
          ↓
统一证据装配：主块、必要邻块、明确关联条款
          ↓
证据缺口判断
    ├─ 现有证据可回答 → 生成
    ├─ 只能回答一部分 → 限定回答并说明缺口
    ├─ 场景歧义影响结论 → 澄清或分场景说明
    └─ 可定位的缺口 → 有限补检POC，未达标则不启用
          ↓
同一证据集合用于模型、引用展示和评测
```

顺序为：阶段0冻结基线 → 阶段1统一证据与评分 → 阶段2适用性和内容类型 → 阶段3确定性关系补证 → 阶段4有限补检实验 → 阶段5发布验收。

阶段4是可否决的独立实验。阶段1至3达标后，即可作为一次基础升级进入阶段5，不等待Agentic实验。

预计1—2个工程工作日，不含付费模型测试等待和人工标注时间。

### 3.2 固定专项题集

原62题集保留，新增24题上下文专项集，每类4题：

| 类别 | 重点 |
|---|---|

每类2题用于开发、2题锁定为盲测，总计12道开发题、12道盲测题。盲测金标由独立验收者保管，开发侧不提供这些答案；如实施者已经读过并据此调参，须补充未见过的题，否则只能称留出集而非盲测。数量是最小探索集，不足以证明广泛泛化效果。

每题标注：问题、可答状态、必要事实、适用条件、允许的来源或来源组合、必须排除的来源用途、支持原文及位置、不可接受的结论。允许多个合法证据组合，不强制唯一文档和唯一措辞。

SAF-08先人工核定问法和适用场景：保留原题历史定义，新增明确房屋市政、明确其他领域及场景未说明的变体。不能为了新系统通过而直接把旧36V判据改成任意数值都接受。

### 3.3 先确认新的回答边界

旧提示词规则3倾向“存在相关片段即回答”，规则4约束整体拒答条件；既有测试还锁定部分提示词逐字不变。拟采用以下行为：

| 证据状态 | 回答要求 |
|---|---|
| 能支撑问题所需结论 | 给出结论及对应证据 |
| 只支持部分内容 | 回答已证实部分，明确缺口，不补造剩余结论 |
| 与主题相关但缺决定性依据 | 不下确定结论；按情况限定说明或澄清 |
| 全部无关或确实没有可用证据 | 保持诚实拒答及知识边界说明 |

这些状态是路由标签，不是正确性的证明。低词面覆盖率和高词面覆盖率都不能单独决定证据充分性。

阶段1只做证据契约迁移，不改变以上回答行为。进入阶段2的行为改动前，须确认用“引用、忠实和边界语义不退化”替代相关旧文字的逐字锁定；同步修订规则3/4与五角色测试，不追加相互矛盾的提示词，也不直接删除旧测试。

### 3.4 阶段完成标准

- 能指出每次实验对应的代码差异、库版本、模型参数、评分版本。
- 旧数据不变，新基线与专项题定义独立存放。
- 知道哪些测试会调用真实模型；测试费用预算尚未批准时只运行纯本地检查。
- 任何无法重建的历史上下文标记“无法完整复核”，不从当前库回填成当时证据。

## 4. 阶段1：统一证据契约、引用范围和评测

预计3—4个工程工作日。这一阶段不改变检索策略，不追求答案涨分。

### 4.1 只保留一份权威证据对象

建议新增小型app/context.py，集中证据结构、装配、去重和长度统计；不引入通用插件框架。

结构约定：

```text
ContextPacket
  contract_version
  kb_revision
  evidence_groups[]
  assembly_stats

EvidenceGroup
  no
  doc_id
  primary_chunk_id
  title
  verified_metadata
  segments[]

EvidenceSegment
  chunk_id
  clause
  pages
  text
  relation_to_primary
```

具体规则：

1. 引用编号指向一个明确证据组，同组只能包含同一文档的内容；跨文档依据必须有自己的引用编号。
2. segments包含主块，以及实际送给模型的补充块；每段保留自己的条号、页码和逐字正文。
3. 当前阶段的relation先支持primary和adjacent_next，后续再增加确有用途的定义、例外、附件等关系。
4. chunk_id只在对应kb_revision下有效。历史引用不能把旧chunk_id直接解释为新库内容。
5. 全局去重使用库版本＋chunk_id；已经单独进入上下文的块不再作为其他组的重复正文。关系仍可保留为引用关联。
6. 模型输入、SSE sources、前端引用正文和评测均从同一对象派生，不分别补邻块。
7. 现有full、excerpt等接口字段如保留，均由主segment派生；它们不再被当作整个证据组的完整内容。新链路明确消费segments，不长期维护两套活动协议。
8. 元数据说明与原文正文分开展示，不能让“人工核定状态”等标签看起来是法规原句。

### 4.2 迁移相邻注入与前端展示

- 将main.py中的装配、邻块注入和去重逻辑移到统一装配入口，删除活动链路中的adjacent_next临时拼接路径。
- 暂时保持原候选集、排序、最多14个主编号组和最多3个新增补充片段，不在协议迁移时顺带扩大窗口。
- build_context从segments渲染；在无行为改动的对照上核对模型所见正文、次序和原有说明文本。
- 引用面板明确显示“本次回答实际使用的主条款／补充条款”，每段有出处；“浏览更多相邻条款”单独展示，不算本次已用证据。
- 复制主条款、复制整组证据语义清楚。整组复制保留每段出处，不把跨段拼接伪装成连续原文。
- 保存新会话时保存证据组快照与库版本。旧会话保留原记录，标注“历史记录未完整保存补充证据”；不得用当前库拼造历史模型输入，不删除历史。

### 4.3 评分迁移

保留旧指标，但调整命名和解释；新旧分数不能互相兑现原验收目标。

| 指标 | 定义或处理 |
|---|---|
| retrieval_hit3 | 继续报告top-3文档命中，只评价排序 |
| ctx_doc_hit | 原ctx_hit的明确命名，表示预期文档进入证据集合 |
| keyword_coverage | 原关键词统计保留，标为诊断指标，不当语义正确性证明 |
| required_evidence_recall | 已进入证据集合的必要证据单元数／该题必要证据单元总数，支持允许的替代证据组合 |
| citation_id_validity | 引用号是否存在于本次证据集合 |
| citation_support | 被引用的主张中，有完整支持依据的比例；含主体、数值、条件、时效检查 |
| answer_support_coverage | 需要证据的主张中，有有效引用且被支持的比例，防止只挑容易引用的句子评分 |
| applicability_error | 使用不适用的文件或条件作结论依据的题数 |
| over_refusal_rate | 当前库经人工确认可回答但系统错误放弃结论的题数／当前库可回答题数；部分缺答另列 |
| unsupported_answer_rate | 人工确认当前库不足以支撑所问结论却被系统作确定回答的比例 |
| answer_correctness | 人工校准后的结论、条件和范围正确性，独立于检索排名 |

没有对应题目时，分母为0必须显示N/A或未覆盖，不能显示100%。

工具安排：扩展run_eval.py保存新协议和计时数据；新增一个独立的评测检查入口，读取结果与固定验收条件，遇到失败、缺测、缺done事件或待人工复核时返回非通过。不得把run_eval当前“请求没失败所以退出0”当作质量验收。

### 4.4 负例与浏览器验证

必须覆盖：

- 越界引用号；编号合法但原文不支持；关键词齐全但主体或条件错误。
- 相邻块原文未进入公开证据集合；重复补证；没有next；跨文档错误归到同一编号。
- 输入段数为0、数据库查询0行、测试没有收集到用例，均不能假通过。
- 对照原PDF核定的关键数值与表格，不只拿抽取文本和数据库互证。
- 浏览器实际完成普通回答、跨块引用、展开、复制、历史恢复和移动端查看；检查控制台及网络请求，不以类型检查代替UI验证。

阶段硬门：证据身份／正文／顺序的一致性测试全部通过；新增非法引用负例必须被正确识别；未触发新策略时检索顺序和证据正文集合不变；没有隐藏的补充证据。

## 5. 阶段2：内容类型、适用范围和时效关系

预计3—5个工程工作日；人工核定时间独立计算。

### 5.1 缩小首批范围

先覆盖0069、0070、0078、0079、0080及专项题实际需要的母通知／附件，不一次性给37份文档补满复杂法律属性。

在现有docs_meta.json扩展确有依据的字段：发布机关、文件性质、适用领域／对象、已核定时效、版本日期的具体含义、母通知及版本关系、核定依据。

日期字段不能混用发布日、施行日和核定日；缺值保留未知。未标注不等于已核实有效；na可能表示无独立时效属性，不等于unknown，也不能统一当成附件已经继承母文件全部效力。

### 5.2 内容类型识别

- 建库时利用章节边界标注正文、表格、目录、练习题、说明材料；不能只凭块内出现问号判断。
- 0079练习题区优先人工核定。选项内容不得作为规范性结论证据。
- 横跨正文和练习区的块标为mixed，不能把整块自动当正文；只有定位到经过核验的逐字正文范围后，才允许作为该范围的依据。
- 首轮不大规模重分块、不生成摘要，不修改已有法条文本。分类和关联元数据与正文分开管理。
- 手工标注按文档、章节、原文锚点及摘要核对绑定，不依赖容易漂移的裸chunk_id；锚点找不到或对应多处则建库验收失败，不能静默漏标。

### 5.3 分两步实验，避免归因混乱

A. 先只把已核定元数据进入上下文和引用面板，检索排序不变，观察适用性说明是否改善。

B. 再对候选证据进行类型与适用性处理：

- 练习选项、目录不能充当规范性结论依据。
- 当前问题明确限定领域且文件被明确核定不适用时，不把该文件作为主要依据；比较不同领域的提问除外。
- 未知范围不能自动等同不适用；不得对全库未知元数据整体降权。
- 同主题、适用范围都可能成立但结论有差异时，保留独立证据，说明条件差异或请求澄清，不自动选择数值最严或日期最新的文件。
- 角色只改变表达侧重，不决定文件适用性和法律效力。

BM25、向量和改写重检共用同一套证据类型与适用性逻辑。不能只修BM25而让向量路径绕过；词面coverage仍保持原含义，另报证据状态，不把类型过滤结果伪装成新的BM25覆盖率。

### 5.4 安全构建数据库和索引

现有build_kb.py会先删除目标数据库；build_vec_index.py固定读取和写入活动kb路径。必须先增加明确的输入／输出路径参数，让流水线在独立制品目录运行。

- 先使用build_kb已有独立输出能力构建候选数据库，再让向量工具读候选库、写候选索引。
- 只有当chunk_id、anchor和正文完全一致时，才可复用经核验的向量索引；任一编码输入改变，重建对应索引。
- 元数据增加后，同时调整SQL写入和BM25／向量读取，改用显式列名，防止位置式INSERT与表结构脱节。
- 校验向量行数、ID集合、重复ID、维度、数值有效性，并与候选数据库实际数据对齐。
- 不运行会先覆盖活动库、随后才提醒重启的旧发布路径。

阶段硬门：专项题中的选项污染、适用范围、版本及附件继承均有可核查依据；安全关键无依据结论不能被平均分掩盖；A与B分别有对照结果。没有足够证据核定的元数据保留未知，不编造。

## 6. 阶段3：确定性关系补证与会话约束

预计3—4个工程工作日。

### 6.1 关系补证

仅处理可明确定位的关系：同条续文、表头／表注、定义、例外、明确引用的条款、已核定的母通知／附件。

实现内容：

1. 在retrieval.py增加参数化的批量读块、读文档元数据及按已核定条款定位读取接口。
2. build_kb将必要关系从核定元数据写入候选库；关系目标不存在、存在歧义或属于其他版本时报告错误，不猜测。
3. context.py按当前问题的证据缺口选择关系，不自动遍历所有相邻块或全图。
4. 初始仅展开一跳；循环引用、重复引用和同一块被多个来源推荐时只读取一次。
5. 同文档补充可加入原证据组，跨文档必须作为独立来源编号，不能冒充原编号的条款。
6. 延续阶段1的总预算：最多14个编号组、总计最多3个新增补充片段；关系补证和旧next补证共享这个预算，不各加3块。
7. 跨文档新增组需要占用原有补位名额；必要证据无法在预算中保留时明确标记不完整，不截断数值、否定词或例外后继续当作充分依据。

### 6.2 长度与位置

第一版统计字符数、片段数、证据组数；有可靠模型usage时记录真实token数，没有时标为不可得，不能把估算当实测。

以阶段0完整上下文长度分布制定字符上限，先约束无界膨胀，不复活“一律截400字”。同样证据首、中、尾置换只作为单独实验；只有复现明确位置收益后才改变默认排序。

### 6.3 多轮处理

保持最近3轮的基本机制，不先加长记忆，不自动总结过去助手答案。

- 当前用户明确说出的对象、地区、时间优先；明确更正覆盖旧条件。
- 历史只用于理解意图，法规事实仍需重新定位当前证据。
- 无关话题切换不得继承旧工程类型或数值。
- 角色切换影响回答视角，不改变已有事实的证据效力；保存每轮实际角色用于解释历史。
- 如果要发送历史引用定位，只发送已存的库版本和块ID，服务端验证后重新读取；不能信任浏览器提交的原文或“有效”标记。

先用专项题验证现有改写能否满足；只有出现可重复失败时才增加结构化会话约束字段，不为尚未出现的问题建立长期记忆系统。

阶段硬门：目标跨块问题必要证据召回改善，补证可追溯且不越界；循环、超预算、无目标均能终止；历史约束不能成为未经核验的新法规事实。

## 7. 阶段4：有限补检POC，可否决、不阻塞基础版

预计3—5个工程工作日。仅在前3阶段后仍有可定位的失败时启动。

### 7.1 进入实验的条件

- 仍存在“库内确有证据，但固定装配找不到或缺少决定性条款”的稳定案例。
- 类型和范围错误已经可以与召回缺口区分，评测能观察实际证据集合。
- 额外模型调用预算和首字延迟容忍度已确认。

如果主要问题是源文件未收录、OCR漏抽或人工元数据未核定，不上工具循环，回到数据问题。

### 7.2 第一版不是无界Agent

只允许以下只读动作：按问题补搜、读取候选条款、读取已核定元数据。无外网搜索、文件写入、命令执行和任意SQL接口。

拟议预算：

- 常规链路之外，最多新增1次模型规划请求；原查询改写的费用仍单独计入。
- 最多2次只读工具调用，其中至多1次补检索；不递归调用模型继续规划。
- 最多新增2个片段，且必须服从阶段3的全局3个补充片段上限，不能叠加超额。
- 额外墙钟耗时暂定上限3秒，作为待测工程参数，不是承诺一定达标。超时取消后续动作，沿用已核验的证据并按证据状态回答。
- 无新增证据、来源不适用、预算耗尽、条款定位歧义时停止。

规划输入只能包含用户问题、必要历史约束、候选元数据和实际证据；输出限定为缺口类型及白名单动作参数。工具名、ID、数量、长度在服务端验证，返回正文按资料处理，不能执行其中的指令。

原文检索结果、用户历史、工具结果都不拥有修改系统规则或扩大工具权限的能力。测试包含文档内的指令性干扰文本，但不宣称简单分隔符能够彻底解决提示注入。

### 7.3 与流式输出的关系

所有补检与证据定稿在首次答案delta之前完成，期间只发送真实状态提示。sources一旦发出并开始答案流，就不静默改编号或替换证据。

本轮不默认加入“完整答案生成后再由另一个模型审核并重新生成”，因为它会新增费用和延迟。引用支持性先做离线评测；不能把答案已流出后的自检当作错误从未暴露。

### 7.4 保留或否决

至少比较阶段3固定链路与阶段4有限补检，分别观察触发题和未触发题。

- 如果只有单次收益、费用明显增加或安全性变差，结论为不确定或否决，不继续堆轮数。
- 若自然流量触发比例超过预期，按实际数据报告，不能预先写成低于10%。
- POC策略只存在于离线实验入口或隔离候选版本；选定后主链路只保留一种实现，不堆长期生产开关。

## 8. 统一验收、对照与费用管理

### 8.1 测试分层

| 层级 | 内容 | 是否允许替代下一层 |
|---|---|---|
| 纯本地 | 装配、字段、去重、预算、状态、评分负例、索引检查 | 不允许 |
| 固定证据回放 | 相同问题及候选，仅改变装配或元数据呈现 | 不能替代端到端 |
| 本机真实服务 | 原62题、专项开发题、多轮与状态题、异常路径 | 不能替代浏览器体验 |
| 浏览器 | 引用、复制、历史、SSE、断流、移动端、控制台 | 不能代替答案人工审查 |
| 发布后 | 新实例的真实版本、冷／热启动、少量问答及引用 | 不用本机结果冒充线上通过 |

现有qa14、混合检索守卫、角色守卫、相邻条款测试继续使用，但以实际收集到的用例数为准。需要服务、会触发模型或会修改埋点的脚本，必须按真实性质分类，不能一律当作免费单测。

### 8.2 公平对照

- 阶段1比较协议迁移前后；阶段2分别比较仅元数据与类型／范围策略；阶段3比较关系补证；阶段4单独比较有限补检。
- 固定语料与模型参数，A/B请求交错，记录失败和服务异常，不能只保留成功样本。
- 最终候选至少进行3轮配对验证，报告逐题胜／平／负和每轮结果，不把重复调用当成增加了独立题量。
- 最终完整对照为62题主集＋12题盲测、2个版本、各3轮，即最多444次回答请求。若对照的模型和环境可比性不足，旧结果不能充当这444次中的对照。
- 444不包含开发调试、阶段性实验和额外规划／改写调用。若费用不足，先做预先约定的小样本试验，结论标为探索性；不能少测后仍称完整验收。
- 金额上限依据实际服务计价预先确认；达到金额或请求上限即停。重试计费也计入上限，不补跑到全绿。

### 8.3 硬门与软门

硬门：

1. 模型、引用和评测的证据身份与正文范围一致；所有引用编号存在。
2. 专项安全组不得出现无依据数值、关键禁止条件遗漏、明确不适用来源冒充依据。任何此类失败都需逐例处理，不能被总体均分抵消。
3. 原拒答和边界组每轮通过人工语义复核；新增缺证组不得把“库内没证据”写成“法规不存在”。
4. 无测试、无证据、分母为0、缺done或请求失败均不得伪装成通过。
5. 数据库、索引、元数据和对应版本一致；当前配置确实加载待测制品。
6. 所有功能类型必须有正、负对照。某类功能未测，报告未验证，不补一个默认PASS。

软门，用于选择方案而非保证书：

- 候选在目标失败组有可重复改善，且总体主张支持性和必要证据覆盖不低于新测对照。
- 未触发补检的路径，首字与总耗时P95相对同机新测对照增幅目标不超过10%；超过时先定位，不能直接归因模型波动。
- 确定性装配阶段的平均上下文字符数增幅目标不超过10%；超出要提供证据收益理由，不能靠硬截条款满足指标。
- 有限补检路径单列延迟、规划请求数、工具调用数和费用，不把其开销藏入全量平均数。

旧fact_all_ok、旧top3目标继续原口径报告，新指标独立展示。因为适用性修正造成的旧指标变化，必须有原始依据和固定的新判据解释，不能简单放宽阈值。

### 8.4 计时与诊断

分别记录请求开始、检索结束、证据定稿、首个非空答案delta和done时间；使用单调时钟。客户端首字计时以完整解析SSE事件为准，不依赖某个网络分片碰巧包含字符串。

记录冷启动与热运行结果。生产默认只记录必要聚合指标和版本标识，不新增原始问题、完整对话或模型内部推理的长期日志。离线证据轨迹留在本机，分享前检查敏感信息。

## 9. 阶段5：知识库完整性、发布与回退

预计1—2个工程工作日，上线窗口另行确认。

### 9.1 制品与启动检查

- 将代码、数据库、向量索引、元数据、必要关系和制品清单作为同一版本交付。
- 清单记录经核验的制品摘要；其参照是阶段0或随后人工验收的制品，不是随手重算自身哈希即宣布可信。
- 启动时校验向量与数据库ID对齐、关键文件摘要、元数据结构和关系目标。全文哈希检查不放在每个请求上。
- 检索器／tokenizer本地文件记录来源和摘要。远程LLM只能记录实际配置和服务返回的版本信息，不能声称验证了不可见的模型权重。
- 只有向量制品失败而SQLite及其证据仍可信时，允许明确降级BM25；SQLite证据或制品版本不可信时，不继续提供看似正常的引用问答。
- 健康检查报告真实状态，不泄漏密钥和内部敏感路径。

### 9.2 切换与回退

1. 在独立目录建好候选制品，完成数据库、索引和本机服务验收。
2. 经单独上线授权后，暂停接收新请求并处理完在途请求；整体切换代码和知识库制品后重启，避免缓存向量对应旧数据库。
3. 核实新实例真实加载的版本，不只看HTTP 200。
4. 实际浏览器验收主流程及引用；至少覆盖一题常规、一题相邻证据、一题适用范围、一题拒答。
5. 失败时恢复上一套完整代码和知识库制品，不只恢复某个Python文件，不删除用户会话或埋点数据。

任何git提交、推送、线上重启、覆盖服务器目录和发布动作，均不由本计划自动授权。
