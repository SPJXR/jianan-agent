## 一、上次组会以来的主线工作（一句话）

9-26 组会时规划的「评测集扩充到 50+ 题」已落地为 **62 题自动评测集**（55 事实题 + 4 拒答题 + 3 边界题），用它跑出的全量评测暴露了 4 道表格型文档题集体失败——定位出共同根因（表格被定长硬切）后完成 **R2 迭代：表格感知分块 + anchor 语义锚点**，综合达标率从 **50/55 提升到 53/55**，达成预设验收线（≥53）。本轮的另一半工作是**把测试体系从"70 项断言"升级为"五层测试架构 + 62 题自动评测"**，下文重点展开。

## 二、R2 主线成果（浓缩版）

| 指标（62 题端到端） | v5.1 本地 | v5.1 线上 | R2（v5.2）本地 |
|------|:---:|:---:|:---:|
| 检索 top-3 命中 | 53/55 | 53/55 | 54/55（评测集修正后 55/55） |
| 上下文块命中 | 52/55 | — | 54/55 |
| 答案要点全覆盖 | 51/55 | 52/55 | 53/55 |
| 引用标注率 | 54/55 | 54/55 | **55/55** |
| **fact_all_ok（综合达标）** | **50/55** | **51/55** | **53/55，达标** |
| 中位延迟 / P95 | 1.48s / 2.55s | 1.79s / 3.24s | 1.94s / 3.7s |

- **根因**：表格型文档（如《严重缺陷清单》三列表格）被 700 字符定长硬切后，类别标题与明细行分离，块内横跨 3~5 个类别，关键词凑不齐，答案块沉到第 24~28 位（检索窗口 14 位之外）——**问题不在检索算法，在语料形态**。
- **方案**（ADR-005）：三阶段分块流水线（行分类→组构建→合并打包）+ anchor 语义锚点列（正文逐字原文不变，414/414 断言）+ 检索窗口 14→16（POC 四档扫描定案）+ 同文档补位 ≤6 契约修复。
- **直接效果**：三道目标题答案块排名 28→7、28→3、20→2；逐字契约构建时全量校验通过。

## 三、测试体系全景（本轮重点）

### 3.1 五层测试架构

经过 23 天迭代，测试已从"零散脚本"沉淀为**五层架构，累计约 100 项自动化断言 + 62 题端到端自动评测，每次改动全量回归**：

| 层 | 测试套件 | 规模 | 守护什么 |
|----|---------|:---:|---------|
| ① 契约回归层（每次改动必跑） | qa_regression | 14 项 | **产品生命线**：逐字引用、条款编号、诚实拒答、越界拒答——任何迭代不得破坏 |
| ① | iter2 API 契约 | 13 项 | SSE 契约 + 知识库块级快照哈希比对（414 块逐字回归） |
| ② 特性守护层 | iter3 改写 / iter4 混合检索 / iter5 角色化 | 8 + 9 + 15 项 | 各迭代特性：两阶段改写、HYBRID on/off 对照零回归、角色模板逐字节一致与非法参数回退 |
| ③ 数据实验层（POC） | poc_r2_chunking 等 5 套 | 55 题代理评测 | 方案选型先用数据说话：窗口四档扫描、旧库同口径对照、量化一致性 19 题、相似度分布 |
| ④ 端到端评测层 | run_eval + 62 题评测集 | 62 题 | 五指标自动打分（见 3.2），本地 + 线上双环境 |
| ⑤ 诊断工具层 | diag_* 系列 4 套 | 按需 | 测试失败时定位根因：向量排名、SSE 装配、新旧库排序对比、补位顺序 |

分层逻辑：**① 保证不退步，② 保证特性不丢失，③ 保证决策有依据，④ 保证整体达标，⑤ 保证失败可归因**。

### 3.2 端到端评测怎么打分（62 题自动评测）

每道事实题由评测脚本自动判五个指标，全部通过才算该题达标（fact_all_ok）：

| 指标 | 判定内容 | 防什么 |
|------|---------|-------|
| retrieval_hit3 | 标准文档进检索 top-3 | 检索层失效 |
| ctx_block_hit | 答案块进入最终上下文 | 装配层截断丢失 |
| answer_full_cov | 答案要点覆盖率 ≥1 | 模型漏答要点 |
| citation_rate | 回答附正确条款引用 | 编造条款号 |
| fact_all_ok | 以上全部 + 引用正确 | 单项好不等于整体可用 |

另有 4 道库外拒答题（须诚实说"未找到"）+ 3 道越界题（须拒绝回答），防止"为达标而瞎答"。

### 3.3 双环境评测与防作弊设计

- **本地评测与线上评测同题同判**：v5.1 本地 50/55 vs 线上 51/55，差异仅 1 题（环境噪声级），说明评测可复现、不挑环境。
- **评测防作弊**：返回给评测打分的来源摘要只用纯正文（anchor 锚点不参与覆盖率计算），检索侧的改进不会被评测口径虚高——**测出来的每 1 分提升都是真实的**。

## 四、测试驱动的三个故事（本轮最有价值的体会）

### 故事 1：回归测试逮住了一次"改 A 坏 B"（DEF-04）

扩检索窗口 14→16 后，**此前已修复的一道题再次失败**——检索分 1.00（材料都在上下文里）但模型输出"未找到"，且两次复现。逐层诊断（诊断层脚本上场）：窗口变大使同文档补位从 6 条涨到 8 条，上下文膨胀到 16 条，排在第 5 位的答案块被前置噪音淹没。按 ADR-004 原定契约补 ≤6 截断后恢复。

**体会**：回归测试的价值不只在"发布前把关"，更在**跨迭代捕捉隐性破坏**——这道题修复于两周前，没有这层回归，它坏了我们可能一个月后才发现。

### 故事 2：系统被冤枉了——评测集自身也要 review（DEF-09）

"考核合格证书由谁签发"判失败，但系统检索 top-3 全部命中正确文档。核实后发现是**评测集漏登了一本同名证书文档**——属标注遗漏而非系统缺陷。修正标注、复测通过、修正依据写入决策记录。

**体会**：评测集也是数据，也会有 bug。判失败先问"是系统错了，还是题错了"，**改判必须有书面依据**，不能为了让数字好看而随手改题。

### 故事 3：三连测区分"系统缺陷"与"模型特性"（SAF-07）

一道题的材料已在上下文中，模型却稳定不写出某个标签词。为排除偶发性，同一题跑三遍（三份独立评测文件），覆盖率 0.50 三连一致——确认是 LLM 摘要行为而非检索缺陷，归入"留观察"而非返工。另外两道边缘案例（库外拒答、越界题）持续 4/4、3/3，兜底行为未受本轮改动影响。

**体会**：涉及 LLM 的测试要**区分波动与稳定**——稳定失败才值得当缺陷修，偶发波动不该追。

### 补充：测试自身故障的排除

首轮评测丢 2 题，排查后发现是 API 限流（429）导致空响应，属**测试基建故障而非系统缺陷**——调整请求间隔重跑恢复。教训：读数前先确认测试工具本身没有说谎。

## 六、反思

1. **测试体系的复利开始显现**：9-26 时是"约 70 项断言兜底"，本轮 R2 动了知识库构建、检索窗口、上下文装配三处核心，全量回归一次跑绿——敢做激进改动，是因为摔了有安全网。
2. **62 题评测集是本轮发现问题的功臣**：4 道表格题在旧的 19 题集里根本不存在，扩充评测集直接换来了问题可见性——**评测集的广度决定改进的上限**。
3. 不足：t_p95 3.7s 略超 3s 目标（LLM 波动）；评测集人工标注仍占大头，标注质量依赖 review 流程；埋点数据尚未接入评测闭环。已列入 R1/R3 计划。
