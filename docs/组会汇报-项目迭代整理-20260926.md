## 一、项目是什么

面向建筑施工安全从业者（安全员 / 项目经理 / 监理工程师）的**法规条款即时问答工具**：

- 只基于 34 份建安法规文档回答，**每条结论附条款号与逐字原文引用**，可核查、不可编造
- 解决两个真实痛点：人工查条款慢（10 分钟+）；通用大模型问答会**编造条款号和内容**，在安全领域不可接受
- 技术形态：FastAPI + 原生 JS 的 RAG 系统，DeepSeek API 做生成层，部署于阿里云 Windows Server（2vCPU/2GiB，无 GPU）

**公网地址**：http://8.137.11.193:9000

## 三、按时间线讲三个故事

### 故事 1：上线不是终点，是缺陷的放大镜（9/20-21）

公网发布后用真实问题测试，暴露了 4 类检索缺陷，每一类都走了「现象 → 根因 → 修复 → 回归」闭环：

| 缺陷 | 现象 | 根因 | 修复 |
|------|------|------|------|
| 排序失真 | 「特种作业人员报名条件」答非所问 | BM25 加分未归一化 | bonus 归一化 + 系统提示词要求先通读再作答 |
| 多轮追问稀释 | 按序号连问时后一问答非所问 | 上一问的词摊薄当前问题信号 | 上下文词只扩召回，覆盖率只按当前问题算 |
| 口语词汇鸿沟 | 「挖坑底下干活」查不到（文档叫「有限空间作业」） | BM25 字面匹配跨不过口语↔术语鸿沟 | **两阶段检索**：弱命中时 LLM 先改写口语为法规术语再检索 |
| 兜底误判 | — | — | 「未找到」误判率纳入回归指标持续监控 |

**体会**：测试集要分层（核心题/兜底题/口语题/操作题），口语题最接近工友真实问法，也最暴露问题。

### 故事 2：用数据否决"想当然"的方案（9/22，A 方向混合检索）

导师推荐论文后，我们选了检索增强方向落地。**最有价值的不是最终方案，而是实验过程**：

1. **四方案对比**（14 标注题）：向量单路最强（top-3 100%），但 RRF 融合反而劣于基线（71.4%→64.3%）
2. **为什么融合会失败**：加权网格（VEC_W 0~8）全部 64.3%——BM25 已调优的排序被均匀融合"平均"掉，精确条款查询被拖累。**任何打破 BM25 全序的朴素融合都不可用**
3. **向量阈值能否兜底**：库内外相似度分布重叠（0.493~0.605），不存在可靠阈值——兜底必须维持原判据
4. **最终方案「条件补充」**：强命中（精确查询）完全走 BM25 **零回归**；弱命中（口语题，本就走改写）向量 top5 置前。指标与向量单路持平，换来强命中的完全确定性

结果：top-1 +7.2pp、top-3 +14.3pp，V3 唯一未命中题修复，P95 仅 233ms。**该方案偏离了论文的 RRF 思路，偏离理由与证据写入 ADR-002。**

工程细节：bge-large 意外劣于 bge-small（小语料垂直场景）；ONNX int8 量化 92MB→23MB（服务器无 GPU）；抓到并修复 CLS pooling 误用 mean pooling 的真 bug；HYBRID=0 秒级回滚开关。

部署排障实录（3 坑全记录）：tar 路径嵌套导致服务仍跑旧代码 → import 报错定位；onnxruntime DLL 失败 → 补 VC++ 运行时；transformers 漏列 → 补依赖。每个都经历完整闭环。

### 故事 3：角色化只改表达，不碰契约（9/23，B 方向）

按论文的角色化提示词模板 + PRD 四类用户画像，实现 **5 套角色模板**（通用/安全员/项目经理/监理/政务编辑）：同一问题「桩头凿除有什么规定」，通用版 182 字直答禁限规定，项目经理版 353 字补充管理流程与责任划分。

设计重点在**产品生命线保护**：逐字引用、诚实拒答等 6 条契约规则在所有角色模板中逐字保留（回归逐句断言）；通用模板与现网提示词逐字节一致；非法角色参数自动回退。**检索层零改动，全量回归原样通过。**

## 六、一点反思

1. **POC 数据驱动的选型**避免了"上了论文方案但效果更差"的尴尬——RRF 在本语料上就是劣化的，实验半天省掉了返工
2. **契约思维**（逐字引用、诚实拒答）让每次迭代都有不可破坏的底线，角色化这类"看似要动回答层"的改动因此变得安全
3. 不足：评测集还太小（19 题），很多结论（如量化噪声不劣化）样本量有限；埋点数据尚未真正用于驱动决策。这两点是下一轮的优先项
