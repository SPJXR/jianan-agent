# 交付前自查：随包照片的肖像合规与三处口径不实（2026-10-21）

记录人：开发本人（AI 助手协助取证与改闸）。这一页写的是**当天自查发现的缺陷**，
不是对外宣传材料，所以按现象—根因—处理—怎么保证不再犯的顺序写。

## 一、触发点

异机核验结果回传后，先把核验方指出的两处问题改掉（测试脚本写死开发机浏览器路径、
无 Key 环境下迭代3 被判 FAIL），提交 `57abbdc`、`6f5bec7`。
改完继续自查包内材料，把三份带图的 PDF 里的图片逐张抽出来看——问题在这里。

## 二、发现：包自己打自己的脸

`05_补充成果材料/建安智能体_一线试用成效小结.pdf` 第六节标题是"现场使用实拍"，
内嵌 2 张项目部办公室原片。两张都是 1706×1279，画面里：

- 前景人物侧脸清晰，戴眼镜，占画面近三分之一；
- 第二张还有一名站立工人和一名从显示器后露出半张脸的人；
- 右侧 27 寸显示器上开着微信聊天窗口，气泡文字在原片分辨率下可辨；
- 桌面上的手机、纸质记录表上的手写字迹。

而**同一个压缩包的根 README** 里写着：

> **不随包提交**：2 张现场照片 —— 含可识别的真人面部，规范第八/九部分要求肖像使用须有合法依据

也就是说，README 声明"已移到包外"的两张照片，被 `md2pdf` 原样嵌进了另一份随包 PDF。
照片确实以改名后的副本躺在 `_不随包提交_身份与原件/` 里，包内那份也确实在。
两边都是真的，所以这不是措辞问题，是**交付物自相矛盾**，而且涉第三人肖像与私人聊天内容。

## 三、根因：闸有盲区

包自检里的"身份词"闸只扫 PDF 的**抽取文本**。文字里当然没有"面部"这种东西，
所以它一路绿灯。此前给异机核验回传件补过一道 Windows OCR 闸（把截图里的字认出来再扫），
但那把尺子只量了别人回传的图，**没量自家包里的内嵌图**。
`md2pdf` 嵌图走的是原字节直传（实测内嵌流 sha256 与源文件完全一致），
这恰好给了一个不依赖识别能力的判定办法。

## 四、处理

1. 随包只留一张**局部裁切**：从原片取 (700,760)-(1330,1279)，630×519，
   画面是办公桌、手、纸质记录表与键盘，不含任何面部，也不含那块开着聊天的显示器。
   放大 2 倍复核过手写字迹不可辨。第六节标题改为"现场使用（局部）"，
   并在图下写明"原片中可识别的真人面部、电脑屏幕上的第三方聊天内容均不在随包材料内出现；
   未打码原片与盖章原件一并留存备查"。
2. 新增**肖像闸**：以两张原片的 sha256 为禁止基准，扫包内全部 PDF 的内嵌图、
   全部散落的 jpg/png，以及作品包内的图片条目。基准文件缺失、扫描张数不足 12、
   基准不足 2 项，都按失败处理——闸不许静默空转。
   本次运行覆盖 21 张图、命中 0。
3. 正对照：拿修复前的旧提交件（`_已作废_勿上传_…_20261021.zip.bak`）跑同一套哈希判定，
   必须报红。结果 `内嵌图 2 张，命中禁止原片 2 张`，通过。
   新包上的 0 命中因此才是"真 0"，不是"没扫"。

## 七、留给下一次的教训

图片是文本闸的天然盲区，而"这条声明说某文件不在包里"这种话，
只要那个文件以另一种形态（改名、内嵌、打进子包）在包里出现过，就是硬伤。
以后凡是"某物不随包"的声明，都要有一条按字节哈希的闸去顶，不能靠人记得。
