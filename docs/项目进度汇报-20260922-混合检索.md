## 三、方法论：用数据选方案，而不是拍脑袋

本轮最有价值的部分是**方案选型完全由实验数据驱动**，共做了 4 组对照实验（14 道标注题 + 5 道库外题）：

### 实验 1：四方案召回对比

| 方案 | top-1 | top-3 | 结论 |
|------|-------|-------|------|
| BM25 基线 | 71.4% | 85.7% | 现状 |
| 向量单路（bge-small） | **78.6%** | **100%** | 最强 |
| 向量单路（bge-large） | 57.1% | 78.6% | **意外劣于 small**——小语料垂直场景下大模型反而引入噪声，且体积 14 倍，淘汰 |
| RRF 融合 | 64.3% | 92.9% | **劣于基线**，否决 |

### 实验 2：为什么朴素融合会失败（本轮关键发现）

RRF 和加权融合（VEC_W 0~8 全网格）**全部劣于 BM25 基线**。原因：BM25 的排序已经过两轮调优，均匀融合会把强命中题（精确条款号查询）的优质排序被向量路「平均」掉。**结论：融合不能作用于排序全序。**

### 实验 3：向量阈值能否做兜底？

对库内题与库外题的 top-1 相似度分布分析：库内 min=0.493，库外 max=0.605——**两分布重叠，不存在可靠的单一阈值**。结论：库外「未找到」兜底仍由 BM25 覆盖率判据 + 生成层诚实作答承担（与 V3 一致），向量路不参与兜底。

### 实验 4：最终方案——「条件补充」融合

不打破 BM25 排序，只在**弱命中分支**（原本就触发 LLM 改写重检的场景）引入向量：

- **强命中**（覆盖率 ≥ 0.5，精确条款查询）：完全走 BM25 原排序，向量不参与 → **零回归风险**
- **弱命中**（覆盖率 < 0.5，口语题场景）：向量 top-5 置前 + BM25 top-3 追加

验证结果：top-1/top-3 与向量单路持平，MRR 仅低 0.012，换来强命中场景的完全确定性。**该方案偏离了论文的 RRF 融合思路，偏离理由与实验证据已写入决策记录（ADR-002）。**

## 四、工程落地要点

| 环节 | 做法 |
|------|------|
| 模型选型 | bge-small-zh-v1.5（512 维），ONNX int8 量化后 92MB→23MB |
| 量化验证 | 19 题排序一致性验证：doc 级指标不低于 fp32 基准，单次编码 3.3ms |
| 部署形态 | 服务器无 GPU，纯 CPU 推理；检索延迟增量 <5ms，P95 仍 233ms |
| 回滚开关 | 环境变量 HYBRID=0 秒级降级回 BM25 单路，无需回滚代码 |
| 降级保护 | 向量组件加载失败自动回退 BM25，不影响服务可用性（部署当天实际触发过一次，按设计工作） |
| 回归保障 | 新增 iter4 混合检索回归测试 9/9；存量测试全绿（qa_regression 14/14、iter1 11/11、iter2 13/13、iter3 8/8） |

## 五、部署过程遇到的真实问题（已全部解决）

1. **tar 解压路径嵌套**导致服务仍跑旧代码——通过组件级诊断（import 报错定位）发现并修复
2. **onnxruntime DLL 加载失败**——Windows Server 默认缺 VC++ 运行时，补装后解决
3. **transformers 依赖漏列**——本地开发环境已装故未暴露，已补进 requirements

每个问题都经历了「现象 → 定位根因 → 修复 → 验证」闭环，过程记录在验收文档中。
